# Story 20.2: Start-up and memory measurement

As the owner, I want cold start and idle memory measured the way the baseline defines them, on each OS, so that the existing limits are checked and not relaxed.

**Assumptions**
- Limits are unchanged (NFR-2): "App cold start to Sign-in screen" ≤ 3 s; idle memory ≤ 300 MB, counted over the **whole process tree** (main, renderer, GPU, utility and helper processes).
- Cold start means: process launched with an empty OS file cache where the OS allows it (first run after reboot, or `purge` on macOS, dropping caches on Linux, a fresh boot on Windows), to the first paint of the sign-in screen.
- Idle means: signed-in, dashboard shown, no user input for 60 s, three runs; every run must be ≤ 300 MB, the median is reported for context.
- Hardware is a mid-range machine of the owner's choice; spec recorded with results. Where the baseline Tauri figures exist, they are measured on the same machine for context, not as the target.

**Acceptance Criteria**

**Given** each OS and package from 19.3
**When** cold start is measured five times
**Then** the report gives each run, the median and the worst case; the gate is every run ≤ 3 s, so a single run above 3 s is FAIL. The median is context only.

**Given** idle memory
**When** sampled
**Then** the report states the tool used, the process list included, and the sum in MB; on Windows and Linux the sum uses private/proportional memory, and on macOS the sum uses the footprint figure, with the method written once and used for both apps.

**Given** a result above either limit
**When** reported
**Then** the verdict is FAIL (or CONCERNS only if the owner has approved a written exception in advance); the limit is not changed here and no document in this repository relaxes it.

**Given** the measurement scripts
**When** reviewed
**Then** they live in `electron/scripts/measure/` and write only under `electron/parity-out/perf/`.

**Tasks**
- `electron/scripts/measure/cold-start.mjs`, `electron/scripts/measure/idle-memory.mjs` per OS.
- `docs/planning-artifacts/electron-migration/evidence/performance.md`: method, hardware, results, verdict.
- If FAIL: file mitigation findings (lazy-load main modules, V8 snapshot, disabling unused Chromium features, `asar` layout) against 15.x or 17.x; do not close this story.

**Dev notes**
- Source of the limits: `docs/prd.md` NFR-2. The Tauri baseline for comparison is optional.
- Electron's idle footprint is higher than a system-webview app by design; this is risk 5 in PRD §13.3 and the likeliest FAIL.

**Testing**
- Executed by the implementing team on real machines; not run in this documentation task.

**Prototype unchanged check**
- Require the 14.1 gate. Measurement of the Tauri app reads the installed binary only.
