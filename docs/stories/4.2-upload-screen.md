# Story 4.2: Upload screen

As a Staff member with Upload images,
I want to drop gown photos into the app and see them sent,
So that I can start a batch without leaving the desktop app.

**Assumptions**
- Files are read and sent by the Rust command `upload_files('photo', batchId)`; the webview never holds file bytes (AD-10). The command opens the file dialog; drag-and-drop uses Tauri's file-drop event, which gives paths to the shell.
- Up to 3 uploads in flight; each file carries its own `Idempotency-Key` (NFR-3).
- This story ends at "photos stored". Start processing is Story 4.3. The screen shows the **Start grouping** button but it calls a stub until 4.3 `[ASSUMPTION]`: the button is enabled only when `POST /uploads/{id}/start` exists in `openapi.json`, so the story ships without a dead control.
- Review phase and Processing phase UI come with 4.3 and 4.5. This story builds the Empty phase, the upload list and the rejected-files list.
- Viewer gets the forbidden view (no sidebar item, 403 on direct route).

**Acceptance Criteria**

**Given** the Upload screen (U1, empty)
**When** it renders for Admin or Staff
**Then** it shows the dashed drop zone "Drop gown photos here", **Choose photos** and the rule text "JPEG, PNG or WebP, up to 25 MB each, up to 200 per batch" (Revised 2026-11-14, Story 21.6: no per-batch figure); the empty-state art is not used inside the zone.

**Given** photos are dropped or chosen
**When** `upload_files` runs
**Then** the shell filters by extension and size first (image type is confirmed by the server), sends each file with its own `Idempotency-Key`, emits per-file progress events, and the screen lists "Uploading {n} of {m}" with a bar; **Cancel** stops the queue and keeps the stored ones.

**Given** a file the server rejects (413, 415) or the shell filters out (over 25 MB, over 200 in the batch)
**When** the run ends
**Then** the rejected list shows one line per file with the reason ("Not a JPEG, PNG or WebP", "Over 25 MB", "Batch is full: 200 photos"), the stored ones remain, and nothing blocks starting.

**Given** the connection drops mid-run
**When** the shell sees a network error
**Then** the banner shows, the queue pauses, and on reconnect the same `Idempotency-Key` values are re-sent so nothing is stored twice; a Vitest/Rust test simulates a timeout after a successful store.

**Given** the user leaves the screen during upload
**When** they return
**Then** `GET /uploads/current` restores the stored count and the screen shows the stored photos as a count and thumbnail strip, not as a progress that was lost.

**Given** the file dialog
**When** the shell reads a file
**Then** no copy is written to disk by the shell, and a Rust test asserts it writes nothing under its data directory.

**Given** `klei-img://` image scheme
**When** the thumbnail strip loads
**Then** the shell serves decrypted thumbnails from the API to the webview without writing them to disk and the CSP still has `connect-src 'none'`.

**Given** a Viewer
**When** the route is opened
**Then** the forbidden view shows.

**Tasks**
- Rust: `upload_files`, `klei-img://` handler with 5-minute in-memory cache, progress events, retry on network errors, tests with a mock backend.
- Desktop: Upload screen empty phase, queue list, rejected list, thumbnail strip, dismissal and error handling, tests, axe.

**Checks**
- `cd desktop && npm test && (cd src-tauri && cargo test && cargo clippy -- -D warnings)`
- `cd backend && ./mvnw verify`
- `docker compose -f infra/docker-compose.yml --profile dev up -d --wait && infra/ci/smoke.sh`
- NFR-1: Rust test for no disk writes; bundle secrets scan unchanged.

## Dev record

**Assumptions**
- File bytes never reach the webview. The file dialog opens from Rust (`upload_files('photo')`), so the command set stays 8, the capability file keeps only `allow-<command>` grants and the CSP is unchanged.
- Dropped paths come from the Tauri window drag-drop event and wait in Rust (`Uploader`, 10 s, only while the Upload screen has called `watch`). The webview sends `upload_files('dropped', batchId)` and can never name a path.
- `Idempotency-Key` per file = first 16 bytes of SHA-256(batch, path, size, mtime), hex. A resend after a lost answer, a timeout or an app restart reuses it, so nothing is stored twice (NFR-3).
- Room in the batch comes from `GET /api/v1/uploads/current`; a batch id that is not the caller's current one is `bad_request`.
- `uploads.rs` is the one source file that may use `std::fs`, and only `metadata` and `read` (NFR-1). `contract.rs` now allows that and asserts no other `std::fs` call or write API appears there; every other file keeps the ban.
- Thumbnails load over `klei-img://localhost/{batch}/{photo}` (Windows: `http://klei-img.localhost/…`), held in memory for 5 minutes (max 400), `Cache-Control: no-store`, path parsed as two UUIDs only.
- The 120 s per-call upload timeout (`Config.upload_timeout`) supersedes the `SLOW_PATH` idea for uploads; `Session::call` takes a timeout per call.
- No Start grouping button: `/uploads/{id}/start` does not exist until Story 4.3.

**Done**
- Rust: `uploads.rs` (triage by extension, size and room; 3 workers; retry on offline, timeout, 429, 502-504 with the same key; cancel), `thumbs.rs`, `upload_files` kinds `photo|dropped|cancel|watch|unwatch`, `klei-img` scheme, drag-drop mapping, `tauri-plugin-dialog`.
- Desktop: `bridge.uploadFiles` over a `Channel`, `upload/Upload.tsx` (drop zone, Choose photos, progress, Cancel, waiting line, one line per rejected file with reason, thumbnail strip, stored count, Retry on load failure), route wired in `Shell.tsx`, CSS, 12 Vitest tests with axe.
- Tests: Rust 34 lib tests (9 new upload tests with a multipart mock: part `file` + bearer + key, lost answer then resend with the same key, 503 wait, at most 3 in flight, 413/415 reasons, room left, foreign batch, cancel, single run) and 3 contract tests; Vitest 96.
