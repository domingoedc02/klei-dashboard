# Story 17.1: Photo upload engine

As a Staff member, I want selected or dropped photos uploaded to my current batch with the same validation, retry, cancellation and progress behavior, so that a transient failure does not duplicate or lose stored photos.

**Assumptions**
- Electron main owns native paths, file reads, network calls and upload state; preload exposes only the existing typed `upload_files` contract.
- The API/session layer from 16.2 and Channel-compatible progress path from 15.3 are complete. Files remain memory-only except reads from user-selected paths.

**Acceptance Criteria**

**Given** `photo` or `dropped` is invoked for a target batch
**When** upload begins
**Then** main GETs `/api/v1/uploads/current`, requires response `id === targetId`, rejects 403 as `no_access`, rejects mismatch as `bad_request`, and reads no file before the check passes.

**Given** inspected candidate files and current batch contents
**When** they are triaged
**Then** extension (jpg/jpeg/png/webp, case-insensitive) is checked before size (>25 MiB), then remaining room (200 minus stored count); folders are skipped, unreadable files are rejected, and each file receives exactly one rejection reason.

**Given** eligible files
**When** the upload runs
**Then** no more than three requests are in flight; each is multipart field `file` to `/api/v1/uploads/{targetId}/photos`; `Idempotency-Key` is the lowercase hex of the first 16 SHA-256 bytes over batch, path, length and mtime-ns joined with NUL separators.

**Given** a 429, 502, 503, 504, offline or timeout outcome
**When** a file is retried
**Then** after 3 seconds the identical key is reused and progress reports `waiting: true`; cancellation interrupts waits and in-flight work, stops queued files, retains already-stored results, and emits `{type:'progress',done,total,waiting,photoId}`.

**Given** a server refusal
**When** status is 413, 415 or 403
**Then** 413 maps to `full` if the batch cap is reached, otherwise `dimensions`; 415 maps to `type`; 403 is fatal `no_access`; other unexpected responses are fatal `failed`. Only one run may be active.

**Tasks**
- `electron/src/main/uploads.ts`: port photo/dropped file stat, triage, stable key, three-worker queue, retries, cancellation and progress.
- `electron/src/main/commands.ts`: route `upload_files` kinds `photo`, `dropped`, `cancel` through typed validation; use native photo picker filtered as `Photos` for `jpg`, `jpeg`, `png`, `webp`.
- `electron/src/preload/bridge.ts`: preserve event and summary shape; never return paths or file bytes.
- `electron/test/uploads.test.ts`: assert preflight ordering, triage order, key stability, 3-worker ceiling, retry/waiting, cancellation and fatal/rejection mapping.
