# Story 10.3: Vision verify per group

As a Staff member,
I want the AI to look at the photos in each group and split out any that show a different gown,
So that two gowns that share colour, fabric and pose do not end up in one folder.

**Assumptions**
- Embeddings capture colour, fabric and pose more than silhouette (inference; Story 10.1 measures it). A vision model comparing the photos side by side can tell a wrap bodice from a pleated one. No training.
- Verify runs inside step 2 (Grouping), after `Clusterer.cluster` and before groups are persisted. No new step number: `STEPS` in `Processing.tsx` and the packed `error` step stay as they are. Groups only exist after verify, so `grouped()` (`GroupingService.kt:210`) stays the resume predicate and Retry never re-verifies.
- `GroupingService.group()` (`:215`) today clusters and persists inside one `tx.executeWithoutResult`, and no AI call may run inside a DB transaction (the adapter enforces it: `OpenAiCompatibleAdapter.exec`, `check(!TransactionSynchronizationManager.isActualTransactionActive())`, line 140). So `group()` is split into three parts:
  1. **Load** (`readOnly` tx): read the embeddings for `ids` into `vectors`, and read `Clusterer.threshold(settings.view().sensitivity)`. Returns plain values; nothing managed escapes the tx.
  2. **Cluster and verify** (no tx): `Clusterer.cluster(vectors, threshold)`, then one `compare` call per group of two or more photos. Image bytes are read per photo with `readOnly.execute { batches.image(...) }` exactly as `describeOne` does (`:273`), and each read ends before the call starts. Output: a list of final groups (members, score, verified flag) held in memory.
  3. **Persist** (`tx.executeWithoutResult`): lock the batch (`PESSIMISTIC_WRITE`, "batch gone" check kept; a Cancel can now land during part 2), delete old groups, write the final groups and photo assignments, clear `batch.error`.
- Part 2 is the only place `compare` is called. A provider failure there is caught as `AiProviderException` and makes that group unverified. The `provider(step) {}` helper is **not** used for verify (it turns a failure into `StepFailure` and would fail the batch). The `IllegalStateException` from the transaction guard is a bug, not a provider failure: it is not caught and ends the batch as `internal`.
- Model: `visionModelAdv` when `advanced`, else `visionModel`, the same rule as describe (`AiSettingsRules.kt:67`). No new setting, no migration.
- New port method `AiProviderPort.compare(call, images)` returning a partition. The adapter reuses the multi-image `image_url` data-URI payload of `describe` (`OpenAiCompatibleAdapter.kt:85-111`). New `AiPurpose.VERIFY`.
- Singletons are skipped (no call). Cost: one call per group with two or more photos, each with at most 8 thumbnails (480 px). Estimate 8 to 10 extra calls and 20k to 50k extra input tokens for a 30-photo batch (provider dependent, not measured).
- For a group over 8 photos, send the 3 lowest-mean members, the 3 highest, and fill by upload order, using the similarity matrix already in memory.
- Prompt carries only "Photo n of m" labels, no filename, id, path or client data (NFR-1, same rule as `PromptBuilder`). Ask for a JSON partition: lists of photo numbers that show the exact same gown (silhouette, bodice, neckline, skirt, train), ignoring pose, angle, light and background.
- Failure policy: an invalid partition (an index missing, repeated or out of range), a refusal, or a provider error leaves the group intact and **unverified**. Verify never fails the batch.
- Confidence: a verified group keeps its Story 10.2 score; an unverified group with two or more photos is capped at 89 (never High). The cap is applied in part 2 and stored as the stage-A confidence (`UploadGroup.confidence`) in part 3. Stage B (`ConfidenceScorer.score`, `GroupingService.kt:282`) reads that stored value as `sim` and, after Story 10.2, can only lower it (`sim * (0.7 + 0.3*share)`, share at most 1), so describe cannot lift the cap. No new column, no migration, and nothing to remember across a Retry: the capped number is the stored number.
- No call runs inside a DB transaction (see the three-part split above); one `ai_usage` row per call, stored prompt is a label ("verify group n of m"), never image bytes.
- OPEN QUESTION (V-1): does the real provider accept several `image_url` data URIs in one chat call (like S-1 for embeddings)? Default: yes, as `describe` already does this. A failure shows as an unverified group.

**Acceptance Criteria**

**Given** a group whose photos the provider partitions into two sets
**When** step 2 runs
**Then** the group becomes two groups, each with its own members, rescored with the Story 10.2 formula on its members, positions renumbered, names "Group {n}", and every Photo has exactly one `group_id`.

**Given** a group the provider returns as one set
**When** step 2 runs
**Then** the group is unchanged and counted verified.

**Given** a singleton group
**When** step 2 runs
**Then** no provider call is made for it.

**Given** a partition with a missing, repeated or out-of-range photo number, or malformed JSON
**When** it is parsed
**Then** the group stays whole, is unverified, its confidence is `min(score, 89)`, and processing continues.

**Given** a provider error (timeout, 5xx, refused, unauthorized) on verify
**When** the adapter's own retry is exhausted
**Then** the group stays whole and unverified; the batch does not enter `error`.

**Given** a group of 12 photos
**When** the verify call is built
**Then** it carries 8 images chosen as 3 lowest-mean, 3 highest-mean and the first two by upload order not yet chosen, in a stable order, labelled "Photo 1 of 8" to "Photo 8 of 8"; photos not sent stay with their nearest sent member's set (mapped by highest similarity).

**Given** a batch that goes through step 2
**When** `GroupingIT` runs with the stub provider
**Then** every `compare` call observed `isActualTransactionActive() == false` (the stub performs the same check as the adapter and records each answer), at least one call was observed (the test fails if none), and the groups and photo assignments are written by a single later transaction.

**Given** the real adapter
**When** `compare` is invoked inside a transaction (an `OpenAiCompatibleAdapterTest` wraps the call in a `TransactionTemplate`)
**Then** it throws `IllegalStateException("AI call inside a transaction")` and writes no `ai_usage` row; the same guard that protects embed and describe covers `VERIFY`, because `compare` goes through `exec`.

**Given** `UploadBatchService.discard` (it has no PROCESSING guard) removes the batch while verify calls are running
**When** part 3 starts
**Then** the existing "batch gone" `IllegalStateException` ends the run through `run()`'s generic catch, `fail()` finds no batch and does nothing, no group row is written, and no row refers to the removed batch.

**Given** a group whose verify failed and whose stored score before the cap was 95
**When** step 3 describes it with a full taxonomy match (share 1.0)
**Then** the stored confidence is 89 after describe (never above the cap), and a group verified in the same run keeps its own score.

**Given** the usage log
**When** a verify call finishes
**Then** one `ai_usage` row exists with purpose `VERIFY`, outcome and duration, a prompt label holding no filename or id, and the Usage tab filter and the enum guard test (`AiUsageIT`) accept the new value.

**Given** the prompt text
**When** `PromptBuilderTest` inspects it
**Then** it contains only "Photo n of m" and the fixed instruction, none of the sentinel filenames or ids.

**Given** a run with the stub provider
**When** `GroupingIT` uploads six fixture photos that cluster into one group and the stub partitions them into two
**Then** the batch ends in `review` with two groups, both verified, and the Notification text counts the final gowns.

**Given** the leak suite
**When** extended
**Then** a batch against the stub leaves no image bytes in any log, no sentinel in `ai_usage`, and vectors only as envelopes.
