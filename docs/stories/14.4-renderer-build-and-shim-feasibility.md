# Story 14.4: Read-only renderer build and shim feasibility

As the owner, I want proof that the original renderer can be built from `desktop/src` without editing or polluting `desktop/`, and that its one Tauri import can be satisfied from outside it, so that Electron runs the same UI code and not a copy.

**Assumptions**
- The only Tauri import in the renderer is `desktop/src/bridge.ts:1` (`Channel`, `invoke` from `@tauri-apps/api/core`). Its wire shape is known from `desktop/scripts/shots/tauri-shim.mjs`: `invoke(cmd, args)` where a `Channel` argument is sent as `__CHANNEL__:<id>`, events arrive as `{ index, message }`, and the stream ends with `{ end: true, index }`.
- **Option B (preferred; matches AD-24 and `docs/architecture.md` §13.1).** An Electron-owned build config aliases `@tauri-apps/api/core` to an Electron-owned module `electron/src/renderer-compat/core.ts` that exports `invoke` and `Channel` with the same signatures. The module calls **nine named methods** that preload exposes through `contextBridge`; it has no generic dispatch and sends no command name through preload. Output and cache are redirected to `electron/`.
- **Option A (fallback only).** Preload defines `window.__TAURI_INTERNALS__.invoke(cmd, args)` so the unmodified `@tauri-apps/api` bundle runs. A command name then crosses preload, which AD-24 forbids ("no raw command name or arbitrary dispatch crosses preload"). Use A only under the owner-approved AD-24 exception (2026-11-13), and only after the note records why B failed.
- **Option C (last resort).** A copy of `desktop/src` under `electron/`, frozen at the baseline SHA and recorded in `electron/BASELINE.md`; changes only in the copy. Needs owner sign-off.
- `contextBridge` proxies plain values and functions; class instances (`Channel`) do not cross. So the alias module owns the `Channel` class in the page, and passes it only as a plain callback function to a named method.

**Acceptance Criteria**

**Given** Option B
**When** the baseline renderer is built from `desktop/` sources into `electron/build/renderer/` with an Electron-owned Vite config (`root` at `desktop`, `build.outDir` and `cacheDir` under `electron/`, `resolve.alias` for `@tauri-apps/api/core`)
**Then** the build finishes, `git status --porcelain --untracked-files=all -- desktop` is empty, nothing appears in `desktop/dist` or `desktop/node_modules/.vite`, and the output has no reference to `localhost:1420`.

**Given** the built renderer loaded in a throwaway Electron page with the spike preload in `electron/spikes/04-shim/` exposing the nine named methods (the production preload is built and accepted in 15.3, not here)
**When** `bridge.request`, `bridge.uploadFiles` and `bridge.exportGowns` are called from a test page
**Then** the handler receives the same command and arguments the Tauri call carries, a `Channel` argument becomes a callback that receives `{ index, message }` in order followed by one `{ end: true, index }`, and a rejection reaches the caller as `{ kind, message }`.

**Given** the alias module
**When** its source and the preload source are scanned
**Then** no function takes a command name from the page, there is no `invoke`-by-string path in preload, and the exposed object has exactly nine keys.

**Given** Option B cannot satisfy the above
**When** Option A is tried
**Then** the note records the reason and the failing evidence, applies the owner's pre-approved AD-24 exception (preload accepts a command name only from the nine allowlisted names, validated before any handler runs, no other dispatch), and tests that a tenth name fails `bad_request`; Option C is tried only after A is also rejected.

**Given** the resolved dependencies
**When** the build runs
**Then** the note records which `node_modules` resolved (`desktop/node_modules` read-only, or a pinned install under `electron/`), the React and Vite versions, and that `desktop/package-lock.json` is unchanged.

**Given** fonts and assets
**When** the build is loaded from `app://`
**Then** Inter fonts and images load with no CSP violation, and the CSP stays `default-src 'self'; img-src 'self' klei-img: data:; connect-src 'none'; style-src 'self'; script-src 'self'; font-src 'self'` (plus only the 17.5 Windows allowance if spike 6 requires it).

**Tasks**
- `electron/vite.config.mjs`: Electron-owned build config with `root`, `build.outDir`, `cacheDir`, `base: './'`, `resolve.alias`, and `server.fs.allow` limited to `desktop/` and the font directory.
- `electron/src/renderer-compat/core.ts`: alias target, exporting `invoke` and `Channel`; maps each of the nine command names to its named preload method.
- `electron/spikes/04-shim/`: throwaway preload and handler proving B (and A only if B fails).
- `docs/planning-artifacts/electron-migration/spike-7-renderer-build.md`: decision note (B, A or C), versions, what was and was not changed in `desktop/`, the `contextBridge` finding.
- Memlog `decision` entry for the chosen option.

**Dev notes**
- `desktop/vite.config.ts` and `desktop/index.html` are read-only; `index.html` loads `/src/main.tsx`. Pass `root` and an explicit `build.rollupOptions.input` so Vite writes nothing into `desktop/`.
- The existing hash router needs no server rewrite under `app://`.
- Do not copy `desktop/node_modules`. If resolution from `electron/` fails, install a pinned copy under `electron/` matching `desktop/package.json` and record it.
- Gate for 15.3: the shim is built only after this note exists.
- The Electron renderer is a different build of the same source, so "original bundle untouched" is not a benefit of A; the benefit of B is that no command name crosses preload.

**Testing**
- Run the renderer build twice and `git status --porcelain --untracked-files=all -- desktop` after each; both empty. Run the round-trip test against the built output.
- Real-Electron check only; plain Chromium results are not accepted for the `contextBridge` finding.

**Prototype unchanged check**
- Require the 14.1 gate. Record `git diff --stat 51949da2a0f8347c5f1f56fc5d87d8ada6e60643 -- desktop` as empty in the note.
- Visual: baseline harness capture of the Electron-built renderer vs the original renderer for one screen (dashboard default) at 1440×900 shows no differences.
