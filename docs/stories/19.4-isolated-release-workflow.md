# Story 19.4: Isolated release workflow

As the owner, I want Electron releases published by their own workflow and tag pattern to the download site (18.5), with no access to the Tauri release credentials, so that a preview release can never overwrite or confuse a Tauri release.

**Assumptions**
- New file `.github/workflows/electron-release.yml`; triggers only on tags `electron-v*` (the Tauri release workflow runs on `v*`; `electron-v1.0.0` does not match `v*`, so the two are disjoint).
- The release host is the download site (OQ-M3 resolved, story 18.5). The workflow reads secrets `ELECTRON_DOWNLOAD_BASE_URL`, `ELECTRON_DEPLOY_HOST`, `ELECTRON_DEPLOY_USER`, `ELECTRON_DEPLOY_KEY`, `ELECTRON_DEPLOY_KNOWN_HOSTS` and variable `ELECTRON_DEPLOY_PATH` (the site's data directory). None exist yet (OQ-M5), and none is the Tauri `RELEASES_*` or `TAURI_SIGNING_*`. The publish job uses a GitHub environment `electron-release` that needs the owner's approval, and only that job can read the secrets.
- No signing key or certificate is used (internal-use app). The release publishes the five 19.3 artifacts and one `release.json` to the site; the site derives `latest.json` from it.
- Every `release.json` carries `"channel":"preview"` until the owner approves cutover (20.4).

**Acceptance Criteria**

**Given** the workflow
**When** read
**Then** `on.push.tags` is exactly `["electron-v*"]`, there is no `branches` trigger, `permissions: contents: read` at top level and write only on the publishing job, and the job `if` requires the tag to match `^electron-v[0-9]+\.[0-9]+\.[0-9]+(-[0-9A-Za-z.]+)?$`.

**Given** the tag version
**When** compared with `electron/package.json` `version`
**Then** a mismatch fails the job before any artifact is published.

**Given** the build steps
**When** run
**Then** they reuse the 19.3 build (called as a reusable workflow or the same scripts), rerun the 19.2 tests, and fail if any smoke launch fails.

**Given** the artifacts
**When** scanned before publication
**Then** the secret-shaped string scan from 19.2 passes on the artifacts and on the manifest; the scan step runs after build and before the publish step, and the publish step has `needs` on it.

**Given** the publish step
**When** it runs
**Then** it builds with the real `ELECTRON_DOWNLOAD_BASE_URL`, copies the five artifacts by `rsync` over SSH (host key pinned from `ELECTRON_DEPLOY_KNOWN_HOSTS`, no `StrictHostKeyChecking=no`) into a hidden folder `<data>/.<version>.part`, writes `release.json` last (fields `version`, `pubDate`, `channel`, and per file `name`, `os`, `arch`, `kind`, `size`, `sha256`; no URLs, no notes), then renames the folder to `<version>` so the site never lists a half-uploaded version; it never creates a GitHub release and never targets the Tauri release repository.

**Given** a version folder already exists on the site for the tag
**When** the publish step runs
**Then** it fails and overwrites nothing.

**Given** the build output of the publish job
**When** scanned
**Then** the real base URL and token appear in the packaged app only inside the generated config constant, in no log line, and in no uploaded GitHub artifact; GitHub's secret masking is relied on for logs but the workflow also never echoes the value.

**Given** the workflow file
**When** scanned by `electron/test/workflows.test.ts`
**Then** it contains none of `TAURI_SIGNING`, `includeUpdaterJson` or `tauri-action`, and no whole identifier equal to `RELEASES_TOKEN`, `RELEASES_OWNER` or `RELEASES_REPO`.

**Tasks**
- `.github/workflows/electron-release.yml`.
- `electron/scripts/release-manifest.mjs`: writes `release.json` (sizes and SHA-256 per file); no `latest.json` and no `SHA256SUMS.txt`, the site shows the SHA-256 values.
- `electron/test/release-integrity.test.ts`: tag/version check, `release.json` shape and file-name pattern, no URL in it, no duplicate-version overwrite.
- `electron/test/workflows.test.ts`: extend.
- `docs/release-checklist.md` is **not** edited (protected); Electron release steps go in `electron/RELEASE.md`.

**Dev notes**
- Reference only: `.github/workflows/release.yml` (tag `v*`, `tauri-action`, minisign secret, `includeUpdaterJson`) and `infra/ops/key-custody.md`.
- The site's `latest.json` matches what 18.3 reads: version and date only; the page URL is a build-time constant in the app, not in the manifest.
- Not a Gatekeeper fix: SHA-256 values prove integrity relative to the site, not publisher identity. The deploy key is a write-only account on the site's data directory with a forced `rsync` command if the server allows it; this is an owner action.

**Testing**
- Run the unit tests. A dry run on a test tag in a fork or throwaway repository, deploying to a throwaway download-site data directory, is the real check; never use the production site.

**Prototype unchanged check**
- Require the 14.1 gate. `git diff 51949da… -- .github/workflows` shows only added `electron*.yml` files. Pushing an `electron-v*` tag does not start `release.yml` (verified by reading its `tags: ["v*"]` filter and by a throwaway-tag run).

**Dev Agent Record**

Status: partial. Static tests pass; `electron-release.yml` itself has not run: it needs an `electron-v*` tag, the `electron-release` environment with reviewers, the deploy secrets and a real site (OQ-M5), none of which exist yet. Its `test` job uses the same steps as 19.2 and now has the same three fixes (full-history checkout, Electron binary step, build before test); those steps were proven by the green `electron` run `43578750205`, not by this workflow.

Built:
- `.github/workflows/electron-release.yml`: `verify` (tag shape and package version), `test` (19.2 steps on three OS families), `build` x4 (environment `electron-release`; site precheck, release build with the real URL, inspect, secret scan, smoke from each installer, upload to `.<version>.part`), `publish` (environment `electron-release`; `release.json`, scan, checksum check on the site, `release.json` last, rename). Top-level `contents: read` only; no job asks for more; no GitHub release; installers are never GitHub artifacts (only `entries-*.json`, 1 day).
- `electron/scripts/deploy.sh` (`check`, `upload`, `finish`): pinned host key with `StrictHostKeyChecking=yes`, input validation, refuses an existing version, rsync or scp, no delete, secrets never printed or on a command line.
- `electron/scripts/smoke-installer.sh`: the per-OS installer smoke moved out of `electron-package.yml` so the release uses the same code; `release-manifest.mjs sums`.
- `electron/RELEASE.md`: setup table, release steps, failure handling.

Tests: 6 in `workflows.test.ts`, 8 in `release-integrity.test.ts` (fake `ssh`/`scp`/`rsync` recorders). Mutations that failed the suite: installer upload to GitHub, relaxed host key, skipped checksum check, missing existing-version refusal, `environment` removed from `build`.

Not verified: any hosted run; real SSH, `rsync`/`scp` on the Windows runner, `sha256sum -c` and `mv` on the server; the one-approval-per-environment behaviour for matrix jobs; the Windows and Linux legs of `smoke-installer.sh` (only the macOS arm64 dmg ran locally). `ELECTRON_DEPLOY_USER` should be restricted on the server to the data folder; that is not enforced here. A deploy key leaked from the environment could publish a version, so keep the reviewer rule on.
