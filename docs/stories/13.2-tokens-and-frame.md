# Story 13.2: Tokens and frame

As a Staff member,
I want the shell, sidebar and page frame to look like the prototype,
So that every screen sits on the same canvas before screen-level work starts.

**Assumptions**
- Prototype source: `css/base.css` (`:root` tokens), `css/shell.css` (`.shell`, `.side`, `.brand`, `.nav`, `.eyebrow`, `#view`). Desktop: `desktop/src/styles.css`, generated `backend/app/src/main/resources/static/tokens.css`.
- Tokens are generated. Change the DESIGN.md token source, run `node infra/ci/gen-tokens.mjs`, commit the output. Never hand-edit `tokens.css`.
- Rule when sources differ: prototype wins layout and pixels; `DESIGN.md` wins polish (focus ring `#0063bf`, faint meta `#716c66`). A DESIGN.md value that contradicts a prototype pixel is raised as a decision in the Dev record, not applied silently.
- Page max-width must not cap Upload Review (UR-04, owned by 13.7): the frame story removes the cap on the content column, 13.7 sets each screen's own max-width.
- The update banner and the offline banner have no prototype twin. They are judged against DESIGN.md and the handoff colour rule (no warm washes).

**Acceptance Criteria**

**Given** the prototype `:root` custom properties
**When** the Dev record token table is built (`getComputedStyle(document.documentElement)` on both sides)
**Then** every colour, radius, shadow, spacing and type-scale value that the audit rows use matches, or the mismatch is listed with the decision (DESIGN.md source changed and `tokens.css` regenerated, or accepted)

**Given** any screen at 1440x900 (SH-01, `shell.css` `#view`)
**When** the page renders
**Then** content is full-bleed on the white surface with no rounded inset card and no grey frame; page title x matches the prototype (272 px at 1440 wide) and side padding is 32 px

**Given** the sidebar (SH-02, SH-03, SH-08, `shell.css` `.brand`, `.nav`, `.eyebrow`)
**When** it renders
**Then** brand block, nav row pitch, hover and current colours, count badge and the uppercase `Workspace` eyebrow match the prototype pair `dashboard-default`

**Given** the update, update-failed and offline banners (SH-24, SH-25)
**When** they render
**Then** they use neutral or error tokens from DESIGN.md, not the peach/orange-brown warn wash. `styles.test.ts` asserts `.banner` does not use `--color-pill-warn-*`

**Given** `tokens.css`
**When** `node infra/ci/gen-tokens.mjs` runs and `git diff --exit-code` follows
**Then** the file is unchanged, proving it is generated and not hand-edited

**Given** the story's screens are captured on both sides
**When** `node scripts/capture.mjs --side both --only {only}` and `npm run shots:diff -- --only {only}` run
**Then** `geometry.json` shows no `overlap`, `covered`, `glued-text`, `text-clipped`, `offscreen-x`, `page-h-scroll`, `dialog-scroll` or `dialog-overflow` for the desktop side of these screens (`text-ellipsis` only where the prototype truncates the same text), and the run logs no `UNMOCKED` request and no page or console error

**Given** every audit row listed above
**When** the story is done
**Then** the row's Status in `docs/planning-artifacts/ui-parity/audit.md` is `closed` with the fix commit and the after-screenshot path, or the row says `accepted deviation` with the decision it follows (D1 to D5 in the change proposal) and the reason

**Given** each prototype/desktop pair of the story
**When** the lead reads the montage in `ui-parity/diff/`
**Then** the Dev record has one line per pair: `match`, or the remaining difference and why it is fixture-only noise (SVG gown art, fixed clock, mock data). Pixel % is recorded in the Dev record as a trend and is not a gate
