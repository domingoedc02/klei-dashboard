# Story 4.1: Encrypted object storage and photo upload API

As a Staff member with Upload images,
I want my photos to be stored encrypted and safe to retry,
So that no photo is lost, doubled or readable by anyone with database or bucket access.

**Assumptions**
- `ObjectStorePort` and bucket creation exist from Story 1.2; `ObjectCipher` and `stored_object` from Stories 1.3 and 1.4. This story is the first use for photos.
- One file per request (`multipart/form-data`), at most 25 MB, at most 200 Photos per batch, at most two decodes at once (architecture §5.5).
- Upload Batch rules: one active batch per User (`upload_batch.user_id` unique). A User deleted in Story 2.3 has their batch discarded in the same transaction (carries the OPEN QUESTION from Story 2.3: default yes).
- WebP decoding uses TwelveMonkeys; JPEG and PNG use `ImageIO`. Thumbnail 480 px JPEG, metadata stripped.
- Image reads return raw bytes with `Cache-Control: no-store`, fixed Content-Type and `nosniff`.
- Orphan sweep runs nightly in-process; it removes objects with no `stored_object` row and `stored_object` rows with no owner, only if older than 24 h.
- NFR-1 reading: the PRD says "encrypted client-side"; the architecture encrypts in the backend before the object store (AD-7) and the shell never holds a key. Accepted at Gate 4.

**Acceptance Criteria**

**Given** `POST /uploads`
**When** called with `PERM_UPLOAD_IMAGES`
**Then** it creates the caller's batch in phase `empty` or returns the existing one (idempotent); a User without the Permission gets 403.

**Given** `POST /uploads/{id}/photos` with `Idempotency-Key` and one file
**When** the magic bytes are JPEG, PNG or WebP and the header is at most 40 megapixels
**Then** the original and a 480 px JPEG thumbnail are each encrypted with a fresh DEK (`ObjectCipher`: `[version][nonce][ciphertext+tag]`, 64 KB padding, AAD `obj|<bucket>|<objectId>`), written under random UUID keys with Content-Type `application/octet-stream` and no user metadata, and in one DB transaction both `stored_object` rows and the `photo` row (filename, content type and size encrypted) are inserted; on commit failure both objects are deleted; the response is 201 with the Photo id.

**Given** a repeat of the same `Idempotency-Key`
**When** posted again after a timeout
**Then** the first Photo is returned and nothing is stored twice.

**Given** a file over 25 MB, a batch with 200 Photos, a non-image, a mislabelled file, or an undecodable image
**When** posted
**Then** it returns 413 `too_large`, 413 `too_large`, 415 `unsupported_type`, 415 `unsupported_type` (type from magic bytes, never the header) and 415 respectively with problem+json that never echoes the filename; nothing is stored.

**Given** `GET /uploads/current`
**When** called
**Then** it returns the caller's batch with phase, Photo ids and rejected-file count only; another User's batch id returns 404.

**Given** `GET /uploads/{id}/photos/{pid}?size=thumb|full`
**When** the caller owns the batch
**Then** the object is fetched, decrypted and streamed with fixed headers; a tampered or swapped object returns 500 `crypto_failure`.

**Given** `DELETE /uploads/{id}/photos/{pid}`
**When** called
**Then** the row is removed, objects are deleted in `afterCommit`, and an object-delete failure is left for the sweep.

**Given** the sweep
**When** a test plants an object with no row older than 24 h and one younger
**Then** only the older one is removed.

**Given** the JVM
**When** the container starts
**Then** it runs with `ExitOnOutOfMemoryError`, no heap dump and a memory limit (compose `deploy.resources.limits` or `mem_limit`).

**Given** the leak suite
**When** extended
**Then** it uploads a JPEG whose pixels, EXIF and filename carry Sentinels, then lists every S3 key, reads each body and its metadata, and asserts no Sentinel, no content type, no filename; keys are UUIDs; two objects swapped between rows fail to decrypt.

**Tasks**
- Backend: `V9__upload_and_photo.sql` (`upload_batch`, `photo`), `UploadController`, `PhotoIngestService`, `ImageValidator`, `ThumbnailService`, `PhotoReadController`, `ObjectSweepJob`, ArchUnit rule that only `ObjectStorePort` touches the S3 client.
- Test fixtures: tiny JPEG, PNG, WebP, a polyglot file and a 41-megapixel header file generated in code.

**Discrepancies vs story text**
- Migration is `V11`, not `V9`. Read route is part of `UploadController`, no separate `PhotoReadController`.
- Missing `Idempotency-Key` on a photo upload is 400. `PERM_VIEW_GALLERY` cannot read upload previews yet; Story 4.4 decides the gallery read path.
- A rejected file (415 or 413) increments the batch's `rejected` count, outside the version column.

**Shortcuts**
- `list()` pulls the whole bucket per sweep; fine to about 100k objects.
- Whole file is read into memory (25 MB, two at a time); streaming decode is not needed at this size.
