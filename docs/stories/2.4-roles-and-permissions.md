# Story 2.4: Roles and permissions

As an Admin,
I want to see and change what Staff and Viewer may do,
So that each Role fits how the studio works.

**Assumptions**
- Tables `role`, `role_permission`, `permission_epoch` and the default matrix seed exist from Story 1.4; this story adds the endpoints and the screen.
- The matrix edits nine Permissions: the PRD's eight plus `PERM_VIEW_GALLERY` (Gate 5 decision; PRD delta recorded in architecture §12). `PERM_KEY_ROTATE` is not shown and is not editable (architecture §5.4).
- A Role with no Permission locks its Users out: sign-in and refresh are refused (Story 1.6). The Admin Role is locked and always holds every Permission, so the last Admin cannot lock themselves out.
- Helper copy in S6 reads "Admin permissions are locked. Changes take effect right away." The wireframe's "Changes apply next sign-in" is wrong for this design (user ok at Gate 5). PRD FR-6 line gets the same fix in the PRD tidy.

**Acceptance Criteria**

**Given** `GET /admin/roles`
**When** called with `PERM_MANAGE_STAFF`
**Then** it returns the three Roles, the nine editable Permissions and each Role's granted set, with the Role `version`.

**Given** `PUT /admin/roles {roleId, permissions[]}` with `If-Match`
**When** applied for Staff or Viewer
**Then** the Role's set is replaced whole under a lock on its `role` row, the permission epoch is bumped in the same transaction, the Role's Users' refresh families stay valid (the next request returns 401 `token_stale`, the shell refreshes and gets the new `perms`), an Audit Entry names the Role and each Permission granted or revoked, and the response carries the new version.

**Given** the same request for the Admin Role, an unknown Permission, or `PERM_KEY_ROTATE`
**When** sent
**Then** it returns 422 `validation_failed`; a stale `If-Match` returns 409 `conflict`; a caller without `PERM_MANAGE_STAFF` gets 403.

**Given** the matrix screen (S6)
**When** it renders
**Then** it shows 9 Permission rows by Admin, Staff and Viewer columns; the Admin column is disabled and labelled "Locked"; each toggle autosaves with the toast "Permission updated"; rapid toggles on one Role are queued so versions never race; a failed save reverts the toggle with the toast "Couldn't save. Try again."; Loading is skeleton rows and Error is an error block with Retry.

**Given** a Staff User signed in while an Admin removes `PERM_UPLOAD_IMAGES` from Staff
**When** the Staff User makes the next request
**Then** it fails with 401 `token_stale`, the shell refreshes once and retries, `/me` no longer has the Permission, the sidebar drops AI Upload and a direct route shows "You don't have access" (backend integration test and a Vitest for the refetch).

**Given** a Role whose last Permission an Admin switches off
**When** its Users make the next request
**Then** it fails with 401 `token_stale`, refresh is refused, and the shell shows the signed-out screen with "Your account has no access yet. Ask an admin."; switching one Permission back on lets them sign in again.

**Given** a Viewer Role granted `PERM_REPLY`
**When** the Viewer signs in
**Then** Inquiries and the Assistant appear (no role name is checked anywhere; ArchUnit from Story 1.5 still passes).

**Given** the leak suite
**When** extended
**Then** a role change through the API leaves no plaintext Permission name in `role_permission`, the audit table or logs.

**Tasks**
- Backend: `RoleAdminController`, `RoleAdminService` (lock, replace, epoch bump, audit), OpenAPI update.
- Desktop: Roles tab, matrix table, per-Role save queue, `/me` refetch after refresh, tests, axe.

## Dev record

**Done**
- Backend: `RoleAdminService` + `RoleAdminController`: `GET /api/v1/admin/roles` (`{permissions[9 editable], roles[Admin, Staff, Viewer: id,name,locked,permissions,version]}`) and `PUT /api/v1/admin/roles` (whole-set replace, `If-Match` = Role version). Needs `PERM_MANAGE_STAFF`. Rules: Admin Role locked (422); unknown Role, unknown or non-editable Permission (`PERM_KEY_ROTATE`) 422; stale version 409; missing `If-Match` 400; more than 32 entries 422; same set is a no-op (no version bump, tokens stay valid). Replace runs under a write lock on the `role` row, bumps the permission epoch in the same transaction (every access token stale at once, 401 `token_stale`), audits `role_permissions_changed` as `Staff: +PERM_A -PERM_B`.
- Immediate effect: refresh families stay valid after a change; the next call refreshes and `/me` returns the new set. A Role left with no Permission now refuses refresh with 403 once (family revoked, audit `sign_in_no_access`), then 401; Auth Web sign-in already gave 403. One Permission back lets the User sign in again.
- Desktop: Rust `ApiResponse.refreshed` (true after the refresh-and-retry), `Kind::NoAccess` for a 403 refresh (keychain emptied). `Shell` holds `me` in state and reloads `/api/v1/me` after any refreshed response, so sidebar, routes and Assistant follow the new Permissions without a sign-in. `App` has a no-access screen: "Your account has no access yet. Ask an admin." with Sign in again.
- S6 Roles tab in Settings (gated `PERM_MANAGE_STAFF`): 9 Permission rows by Admin/Staff/Viewer, Admin column checked, disabled, "Locked" pill; helper "Admin permissions are locked.
