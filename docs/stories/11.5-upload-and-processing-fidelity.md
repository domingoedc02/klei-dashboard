# Story 11.5: Upload and processing fidelity

As a Staff member,
I want the drop area, the error summary and the grouping progress to read like the prototype,
So that I know what is accepted, what failed, and how far the AI has got.

**Assumptions**
- Prototype: `js/upload.js` (empty, processing). Review is Story 11.6. Current: `desktop/src/upload/Upload.tsx` (dropzone, queue, "Not uploaded" list), `Processing.tsx` (`STEPS`, `Processing`, `Stopped`), tests `Upload.test.tsx`, `Grouping.test.tsx`.
- First task is to confirm the rows marked "verify": the prototype's exact processing percentage rule (it is a mock), whether it shows a Cancel on the processing screen only, and which endpoint `Review.tsx` `discardAll` (line ~136) calls, since Cancel reuses it.
- Dropzone copy (exact): h2 "Drop gown photos here"; hint "JPG, PNG or WebP up to 25 MB each. Upload up to {MAX_PHOTOS} at once and AI groups them."; button **Choose photos**; an upload-cloud icon (Story 11.1). The drag-over state keeps the `over` class.
- U-1 ANSWERED by the user (2026-11-10): the cap stays **200**, not the prototype's 100. No change to `UploadLimits.MAX_PHOTOS` (`UploadBatchService.kt:22`), `MAX_PHOTOS` (`Upload.tsx:13`), PRD FR-8, `epics.md` FR-8 or the strings in `Upload.test.tsx`. The hint reads "Upload up to {MAX_PHOTOS} at once" so it shows 200. This story touches no backend code.
- Error summary: a role="alert" line "{n} file(s) couldn’t be uploaded." ("1 file", "2 files") above the per-file list, then **Retry upload**. The per-file reasons stay with their remedy (stronger than the prototype); **Dismiss** stays.
  - `[ASSUMPTION]` **Retry upload** clears the list and reopens the file picker (`send('photo')`). The app does not keep the failed files, so it cannot resend them. It is hidden when every rejection is `full` (retry cannot help).
- Processing screen: h2 "AI is grouping images" with the overall percentage "{pct}%" beside it; the four steps read "Reading {n} photos", "Grouping images of the same gown", "Tagging silhouette, fabric, neckline", "Writing descriptions"; a skeleton grid of six group tiles below (`aria-hidden`, static under `prefers-reduced-motion`, Story 11.1); a **Cancel** button.
  - `STEPS` (short names) is also read by `Stopped` ("Grouping stopped at step 2 (Grouping)") and by `Dashboard.tsx`. It stays as is. New step labels live in a separate `stepLabel(n, total)` function so those two callers do not change.
  - `[ASSUMPTION]` `pct = floor(100 * ((step - 1) + min(done / max(total, 1), 1)) / 4)`, a pure function `overallPct(step, done, total)`. It does not go down during one run. The bar becomes this overall percentage (`<progress max=100>`, aria-label "Overall progress"); per-step detail stays in the list.
  - Kept as is (stronger than the prototype): "You can leave this screen. Progress shows on the Dashboard." and "Photo thumbnails are sent to your AI provider." (provider disclosure, NFR-1).
- Cancel on processing is destructive: it discards the batch and its photos (same call as Review's discard-all). It first opens a dialog "Cancel grouping?" with the text "This removes the {n} photos from this batch. You can upload them again." and the buttons **Keep grouping** (safe, initial focus) and **Cancel and remove photos**. Uses `openDialog` from Story 11.2.
- OPEN QUESTION (U-2): Cancel does not stop the server run at once. `UploadBatchService.discard` has no PROCESSING guard, the run meets "batch gone" at its next persist, and AI calls already issued are still billed (Story 10.3 covers the same case). Default: accept; a stop signal is out of scope.
- The `error` phase screen (`Stopped`) is unchanged: copy, causes and **Retry** stay.
