# Story 13.4: Shell: top bar, menus and Assistant

As a Staff member,
I want the top bar, bell, search, profile menu and AI Assistant to look and behave like the prototype,
So that navigation and the Assistant feel the same on every screen.

**Assumptions**
- Prototype source: `css/shell.css` (`.top`, `.search`, `.icon-btn`, `.dot`, `.menu`, `.notif`, `.ai-panel`, `.ai-av`, `.ai-sugg`), `js/assistant.js`, `js/main.js` (keyboard). Desktop: `desktop/src/shell/*.tsx`, `desktop/src/assistant/Assistant.tsx`.
- Pairs: `overlay-notifications-{default,empty}`, `overlay-profile-menu-default`, `overlay-search-{results,none}`, `overlay-assistant-{greeting,busy}`, plus the shell frame in every screen shot.
- SH-21 is the one P1: the user's bubble must appear at once, with typing dots, before the POST returns 201. Frontend only; the request and response shapes are unchanged. If the POST fails the optimistic bubble is marked failed with Retry (no API change).
- SH-22: the prototype sends on Enter (Shift+Enter newline); the desktop default is Ctrl/Cmd+Enter through the `enterToSend` preference. Assumed: keep the preference and change only its default for new users to Enter-sends. Existing stored values are not migrated. Flag in the Dev record if the default lives in the backend (then stop, no backend change in this epic). SH-23 (header refresh = new chat) is UI only.
- SH-14 and SH-13 times use the 13.3 formatter (D1 assumption (a)). SH-16 keeps the real `DELETE /api/v1/notifications` call; only the UI parity is checked.
- SH-11 (search skeleton and unavailable text) has no prototype twin: keep, judge against DESIGN.md.
- ST-10 and UR-23 are the same topbar rows seen on Settings and Review; this story closes them.

**Acceptance Criteria**

**Given** the top bar (SH-04, SH-05, SH-06, SH-07)
**When** it renders on any screen
**Then** search is at most 480 px wide with its own icon; the AI Assistant button has the sparkle icon and `aria-expanded`; the bell is a 36x36 icon button with the unread dot only when there are unread items; the profile control shows `EP` initials, name and chevron

**Given** the notification and profile menus (SH-12, SH-13)
**When** they open
**Then** the notification menu is 360 px with title and `Clear all`, an unread dot per item, short times and no footer link; the profile menu is 280 px at the prototype offset with avatar, name, email, icons on Profile settings and Sign out, and a separator

**Given** the search popover (SH-09)
**When** results show
**Then** it is 480 px wide with no group heading, a folder-style icon per hit and the first row not pre-highlighted

**Given** the Assistant panel (SH-17, SH-18, SH-20)
**When** it opens
**Then** it is 400 px at top 64 px; the header has the spark avatar, `AI Assistant`, refresh and close; each AI bubble has the 24 px spark avatar, max-width 88 %; the input is the auto-height textarea with the blue square Send and the hint "Enter to send · Shift+Enter for a new line" (the "Replies are simulated" part is dropped, replies are real)

**Given** a user types a message and presses Enter (SH-21, SH-22)
**When** the request is in flight
**Then** the user's bubble and typing dots are on screen before the POST returns; Shift+Enter inserts a newline; Esc closes the panel when no menu, search or dialog is open. `Assistant.test.tsx` asserts the bubble appears before the mocked 201

**Given** the header refresh button (SH-23)
**When** it is pressed
**Then** a new chat starts (same call as today's footer `New chat`), and the footer button is removed

**Given** Tab in the nav and top bar (SH-32)
**When** arrow keys are pressed
**Then** focus cycles as in `js/main.js`; native Tab still works

**Given** the story's screens are captured on both sides
**When** `node scripts/capture.mjs --side both --only {only}` and `npm run shots:diff -- --only {only}` run
**Then** `geometry.json` shows no `overlap`, `covered`, `glued-text`, `text-clipped`, `offscreen-x`, `page-h-scroll`, `dialog-scroll` or `dialog-overflow` for the desktop side of these screens (`text-ellipsis` only where the prototype truncates the same text), and the run logs no `UNMOCKED` request and no page or console error

**Given** every audit row listed above
**When** the story is done
**Then** the row's Status in `docs/planning-artifacts/ui-parity/audit.md` is `closed` with the fix commit and the after-screenshot path, or the row says `accepted deviation` with the decision it follows (D1 to D5 in the change proposal) and the reason

**Given** each prototype/desktop pair of the story
**When** the lead reads the montage in `ui-parity/diff/`
**Then** the Dev record has one line per pair: `match`, or the remaining difference and why it is fixture-only noise (SVG gown art, fixed clock, mock data). Pixel % is recorded in the Dev record as a trend and is not a gate
