# Story 4.3: Embedding and grouping

As a Staff member,
I want the app to sort my photos into groups of the same gown,
So that I do not group hundreds of photos by hand.

**Assumptions**
- First task is Spike S-1: does `POST /v1/embeddings` on the configured provider accept a base64 data URI as `input`? Test against the real provider by the operator only (the key lives in the encrypted AI settings; a Dev agent never asks for it) and against the stub in CI. Outcome goes to `docs/architecture.md` §8.1 as one line.
  - OPEN QUESTION (S-1): if the data URI is not supported, the one-time fetch URL `GET /api/v1/ai-fetch/{token}` (architecture §7.2, `@TokenAuthorized`) becomes the primary path. Both paths are specified below; the implemented one is chosen by the spike. Default: data URI.
- The PRD example sends an image URL, which suggests the fetch URL may be needed. The URL form carries no persistent URL, is single use, 60 s, held in memory and never logged.
- Embeddings are stored per batch only, encrypted (`embedding.vector_ct`), and deleted at Save or Discard (Story 4.7). Vector length is read from the response.
- Clustering is in memory: cosine similarity with threshold by sensitivity. Initial mapping (tunable, one constant table, `[ASSUMPTION]`): 1 = 0.55, 2 = 0.65, 3 = 0.75, 4 = 0.82, 5 = 0.88. Quality tuning with real photos is a manual step for the operator and is not a CI gate.
- Background work runs on a bounded executor and survives screen changes. A batch left in `processing` at startup becomes `error` (AR-23). A deploy during processing is the same case; the user presses Retry.
- Step 3 (tagging) and step 4 (writing descriptions) arrive in Story 4.4; this story ends with groups named "Group 1..n" and phase `review` with empty attributes `[ASSUMPTION]` so Epic 4 stays shippable in order.
- Only the thumbnail (480 px JPEG) is sent to the provider (architecture §8.1). Never the original.

**Acceptance Criteria**

**Given** `POST /uploads/{id}/start` on a batch with at least one Photo
**When** called
**Then** phase becomes `processing`, a background job starts, a second call while processing returns the same state (idempotent), and an empty batch returns 422.

**Given** processing
**When** step 1 runs
**Then** for each Photo without an embedding, the thumbnail is decrypted in memory and sent to `AiProviderPort.embed`, the vector is stored encrypted with model and dimension, and progress `{step:1, done, total}` is updated; a provider error on one Photo is retried once and then fails the batch with `error_ct` = fixed code and step.

**Given** all embeddings
**When** step 2 runs
**Then** vectors are decrypted in memory, clustered with the sensitivity threshold from settings, each cluster becomes an `upload_group` ("Group {n}", position, confidence from mean intra-cluster similarity scaled to 0 to 100), singletons form their own group, and every Photo has a `group_id`.

**Given** `GET /uploads/{id}`
**When** polled every 2 s while visible
**Then** it returns `{phase, step, done, total, error?}` and, in `review`, the groups with Photo ids, name, confidence band and position; Low-confidence groups come first.

**Given** the Processing screen (U1)
**When** it renders
**Then** it lists the four steps with the current one marked and earlier ones checked, a progress bar for the current step, and the text "You can leave this screen. Progress shows on the Dashboard."; the Reading and Grouping lines show their counts ("Reading 30 photos").

**Given** a provider failure
**When** processing stops
**Then** the screen shows "Grouping stopped at step {n}. Last good {time}." with **Retry**; Retry resumes from the failed step without re-uploading or re-embedding Photos that have a vector.

**Given** the job finishes
**When** phase becomes `review`
**Then** a Notification "AI finished grouping N images into M gowns" is created through `NotificationPort` (a stub that stores nothing until Story 8.1, with an interface test).

**Given** every provider call
**When** it finishes
**Then** one `ai_usage` row is written (purpose `embed`) with outcome and duration, without the image bytes in the stored prompt (store "image {photoId}" only).

**Given** spike S-1 selects the fetch URL
**When** `GET /ai-fetch/{token}` is called with a valid token
**Then** the decrypted thumbnail is returned once and the token dies; an expired, reused or unknown token returns 404 with no body; the ArchUnit rule from 1.5 permits `@TokenAuthorized` on this endpoint only.

**Given** a restart during processing
**When** the backend starts
**Then** every batch in `processing` becomes `error` with code `interrupted`.

**Given** the leak suite
**When** extended
**Then** a batch against the stub provider ends with vectors only as envelopes, no image bytes in any log, and `ai_usage` holds no Sentinel from filenames.

## Dev record

**Assumptions**
- Migration is `V12__embedding_and_group.sql`, not V10 as the story text said (V10 is the Kotlin migration of Story 3.2 and V11 the Photo tables). Both tables reference their parent with `on delete cascade`, so Discard and Delete photo need no extra statement.
- Embeddings live per batch only; Story 4.7 deletes them at Save (Discard cascades already).
- Grouping runs in-process on a bounded pool (2 threads, queue 16), no job table. Progress is held in memory; another node, or a read after restart, sees the fallback `{step 1, done 0, total N}`. A full queue fails the batch with `busy` and answers 503.
- A batch in `processing` is locked: adding or deleting a Photo answers 409. `POST /start` while processing returns the running status; from `review` it answers 409; from `error` it resumes.
- The failure is stored in the encrypted `error` field as `code|step|lastGoodMillis`; the API turns it into `{code, step, lastGood}`. Codes are fixed strings (`unauthorized`, `not_configured`, `refused`, `timed_out`, `unreachable`, `http_error`, `bad_response`, `too_large`, `empty`, `busy`, `interrupted`, `internal`).
- Retry rule: the adapter already retries `retry` failures once; the service adds one retry for the rest except `not_configured`, `refused` and `unauthorized`, which stop at once.
- Clustering is average-link on cosine similarity with the sensitivity threshold (1 to 5: 0.55, 0.65, 0.75, 0.82, 0.88), O(n^3) in memory for at most 200 vectors. Confidence = mean pairwise similarity x 100; a lone Photo is 0 and therefore Low.
- Groups are named "Group n" with empty attributes; tagging and descriptions are Story 4.4. The Notification target is the literal `upload`; `StubNotificationPort` stores nothing until Story 8.1.
- Spike S-1: default data URI kept, `/ai-fetch` not built; recorded in `architecture.md` §8.1 as an OPEN QUESTION for the operator's first real run.
- The review phase has a read-only list of groups in the desktop until Story 4.5 builds the review screen.

**Shortcuts**
- In-memory progress and an in-process pool: a restart turns running batches into `interrupted` instead of resuming on its own.
- Clustering is O(n^3); fine for 200 photos per batch, upgrade if the batch cap grows.
- `error` is a packed string in one encrypted field rather than three columns.
