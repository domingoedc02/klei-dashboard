# Story 14.3: Feasibility spikes

As the owner, I want six open technical questions answered with evidence before any story depends on them, so that keychain, packaging, protocol and persistence choices are decisions and not guesses.

**Assumptions**
- Each spike writes one decision note to `docs/planning-artifacts/electron-migration/spike-<n>-<slug>.md` and one line to the memlog. Throwaway spike code lives under `electron/spikes/` and is not shipped.
- Library and Electron versions are chosen only after checking current releases, maintenance state and platform support on the web on the day of the spike. No version is approved by this document.
- Spikes run on real machines (macOS arm64 and x64 if available, Windows 11, Ubuntu 24.04). A spike not run on an OS records "not verified on <OS>" and keeps the related story blocked.

**Acceptance Criteria**

**Given** spike 1 (OS credential store)
**When** the candidates (`@napi-rs/keyring` recommended; others only if it fails) are exercised
**Then** the note shows on each OS: store, load, overwrite, delete, missing entry as "none", locked/denied store as an error, packaged-app behaviour, and that `safeStorage` plus a file is rejected unless it passes the same checks and stores no plaintext. The chosen library, version and service/account names are recorded; the preview entry uses `co.klei.bridal.electron.preview` with account `refresh-token`, never the Tauri `co.klei.bridal` entry.

**Given** spike 2 (unsigned macOS install)
**When** an unsigned, un-notarized `.dmg` build of a trivial Electron app is downloaded in a browser and opened on a current macOS
**Then** the note records the exact Gatekeeper dialogs, the user steps that allow launch, whether the steps differ on arm64 and x64, and whether replacing the app by a newer unsigned build keeps the credential entry. If launch is impossible without a paid account, the note says so and OQ-M1 is escalated.

**Given** spike 3 (protocol coexistence)
**When** the preview build and the installed Tauri app are both present
**Then** the note shows the preview registers no `klei://` handler, loopback sign-in completes while Tauri is running, the two profiles and credential entries do not collide, and single-instance locks are independent (different app ids).

**Given** spike 4 (no business content on disk)
**When** a trivial Electron app with the planned `webPreferences` loads a page that fetches images and API JSON carrying a sentinel string, and then exits
**Then** a scan of the profile directory (`userData`, cache, code cache, GPU cache, session and local storage, IndexedDB, logs, crash dumps) finds no sentinel; each persistent store is either disabled, redirected to memory, or cleared, and the note lists the exact switches. Any store that cannot be disabled is recorded as a blocking risk for 17.6.

**Given** spike 5 (ZIP writer)
**When** streaming ZIP libraries are compared for a 200-photo, 25 MiB-per-photo export
**Then** the note names one library with version, shows constant-memory streaming, Zip64 support, cancellation with partial-file removal, and fixed-timestamp deterministic output; a rejected-library list gives one reason each.

**Given** spike 6 (Windows image alias)
**When** `http://klei-img.localhost/<path>` is requested from the `app://` renderer under the planned CSP
**Then** the note shows whether a CSP `img-src` allowance for that single origin plus a fail-closed `protocol.handle('http')` works, that other `http` requests are refused, and that no request reaches a real network. If it fails, a custom-scheme-only variant (with the URL rewrite done in the Electron-owned alias module from 14.4, never in `desktop/src/platform.ts`) is described and 17.5 is amended before it starts.

**Tasks**
- `docs/planning-artifacts/electron-migration/spike-1-keychain.md` … `spike-6-windows-image-alias.md`: one decision note each, using: question, method, result per OS, decision, versions checked and date, residual risk.
- `electron/spikes/<n>-<slug>/`: throwaway code, with its own `package.json`; excluded from packaging and from the protected-path allowlist problem (it lives under `electron/`).
- `docs/planning-artifacts/electron-migration/.memlog.md`: one `decision` entry per spike via `uv run _bmad/scripts/memlog.py append`.
- OQ-M1 and OQ-M2 are already resolved in `docs/prd.md` §13.4. This story does not edit the PRD; if a spike contradicts a resolution (for example keychain parity fails for `@napi-rs/keyring`), the note says so and the owner decides.

**Dev notes**
- Rust reference for credentials: `desktop/src-tauri/src/keychain.rs` (service `co.klei.bridal`, account `refresh-token`, fail closed, `SwitchKeychain` memory mode).
- Rust reference for image path set: `desktop/src-tauri/src/thumbs.rs::{parse,mime,Thumbs}`; Windows quirk: `desktop/src/platform.ts`.
- Rust reference for export: `desktop/src-tauri/src/export.rs`.
- Electron specifics to verify, not assume: `protocol.registerSchemesAsPrivileged`, `protocol.handle`, `session` cache and storage switches, `app.setPath('userData', …)` before `ready`, and the packaging tool's macOS target options.

**Testing**
- Each spike records its own pass/fail table. Nothing is automated in CI. These are real-machine checks and are not executed by this documentation task.

**Prototype unchanged check**
- Spike code reads `desktop/` only to copy constants; it never writes there. Require the 14.1 gate to pass.
- No UI is touched; no screenshot comparison.
