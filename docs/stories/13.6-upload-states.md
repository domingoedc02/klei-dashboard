# Story 13.6: Upload: empty, processing and error

As a Staff member,
I want the Upload screen before review to match the prototype,
So that dropping photos and waiting for grouping looks right and the Cancel button is always reachable.

**Assumptions**
- Prototype: `js/upload.js` (`head()` line 28, empty, processing, error), `css/screens.css` `.drop`, `.proc`, `.bar`, `.err-summary`; pairs `upload-{empty,processing,error}`. Desktop: `desktop/src/upload/Upload.tsx` (lines 233-245 hold the "In this batch" block), `Grouping`/processing component.
- UP-09 is the P1: processing shows 30 small 3:4 tiles in 10 columns x 3 rows, gap 6, filling grey as the percentage rises, inside a bordered 640 px centred card, so Cancel stays above the fold.
- UP-05: desktop `MAX_PHOTOS` is 200 (`ux-spec.md:106`), prototype copy says 100. Assumed: keep 200 (real limit), mark the row `accepted deviation`.
- UP-10: the "In this batch / 30 of 200 photos stored" strip is removed from the processing view, kept in the empty phase where it is the only list of staged photos if the current flow needs it (check `Upload.tsx:233-245`). Frontend only.
- UP-13 and UP-14 copy: one sentence "wedding-fitting.heic is over 25 MB and notes.pdf isn't an image. Remove them or convert to JPG or PNG." Dev adapts the file names and limits to the real validation messages; the shape (one sentence, primary `Retry upload` inside the dropzone, no Dismiss) is the contract.
- `upload-loading` and `upload-stopped` have no prototype twin: judged against DESIGN.md.

**Acceptance Criteria**

**Given** the page head (UP-01)
**When** empty, processing and error render
**Then** h1 `AI Upload` has the subtitle "Drop photos. AI groups the same gown, tags it, and drafts a description." 4 px below

**Given** the empty dropzone (UP-02, UP-03, UP-04)
**When** it renders
**Then** min-height 440 px, the `empty-gown-3.png` illustration instead of the cloud icon, h2 26 px with -0.024em tracking, hint and button gaps as in `.drop`

**Given** the processing view (UP-06, UP-07, UP-08, UP-09, UP-10)
**When** 30 photos are processing at 60 %
**Then** it sits in a bordered centred 640 px card with an 8 px blue `.bar` (`role=progressbar`) under heading and percentage, 20 px step marks (done = filled check, now = ring with 8 px dot, todo = empty ring, 12 px row gap), the 10x3 tile grid, and `Cancel` visible without scrolling at 1440x900

**Given** the error view (UP-11, UP-12, UP-13, UP-14)
**When** a batch has rejected files
**Then** the alert comes first as a full-width `.err-summary` (red-tint border, bold title and detail on one line), the dropzone follows with the primary `Retry upload` replacing `Choose photos`, and there is no Dismiss

**Given** the limit copy (UP-05)
**When** the empty state renders
**Then** it shows the real limit (200) and the row is `accepted deviation`

**Given** the story's screens are captured on both sides
**When** `node scripts/capture.mjs --side both --only {only}` and `npm run shots:diff -- --only {only}` run
**Then** `geometry.json` shows no `overlap`, `covered`, `glued-text`, `text-clipped`, `offscreen-x`, `page-h-scroll`, `dialog-scroll` or `dialog-overflow` for the desktop side of these screens (`text-ellipsis` only where the prototype truncates the same text), and the run logs no `UNMOCKED` request and no page or console error

**Given** every audit row listed above
**When** the story is done
**Then** the row's Status in `docs/planning-artifacts/ui-parity/audit.md` is `closed` with the fix commit and the after-screenshot path, or the row says `accepted deviation` with the decision it follows (D1 to D5 in the change proposal) and the reason

**Given** each prototype/desktop pair of the story
**When** the lead reads the montage in `ui-parity/diff/`
**Then** the Dev record has one line per pair: `match`, or the remaining difference and why it is fixture-only noise (SVG gown art, fixed clock, mock data). Pixel % is recorded in the Dev record as a trend and is not a gate
