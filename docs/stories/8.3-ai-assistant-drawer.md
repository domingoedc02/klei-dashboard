# Story 8.3: AI Assistant drawer

As a Staff member with Reply to inquiries,
I want a chat drawer that can summarize new inquiries, draft replies and suggest gowns,
So that I answer faster, while I stay the one who sends.

**Assumptions**
- One global drawer (user decision). The per-thread panel, templates and Share-in-a-reply are dropped for good.
- Context is built by the backend per request from rows the caller can read: at most 20 items of 2 KB each (architecture §8.1). The Assistant has no write path to anything. An ArchUnit rule asserts the `assistant` package imports no write service and no `MailPort`.
- Intent routing is simple keyword matching on the three chips plus free text. Free text sends the last 10 chat messages and a context block chosen by a small rule: mentions of a client name or "inquiry" add the matching Inquiries (found with `Terms.of` on the message, whole words), mentions of gown words add Gowns by the same term index `[ASSUMPTION]`.
- Gown suggestions name existing Gowns only: the server passes the candidate list and validates that every Gown the model names (by id token) exists; unknown names are stripped from the answer.
- Chat history persists per User until New chat (encrypted). `assistant_chat` holds one active chat per User.
- Chips: "Summarize new inquiries", "Draft a reply", "Suggest gowns". The tone chips from the screenshot are dropped.
- Disclosure line (FR-27): "Messages and the inquiry and gown text they need are sent to your AI provider. Nothing is sent by email or changed for you."
- Adds `chat(messages)` to `AiProviderPort`; usage rows use purpose `chat`.

**Acceptance Criteria**

**Given** `GET /assistant/chat`
**When** called with `PERM_REPLY`
**Then** it returns the caller's chat (messages in time order) or an empty chat; other Users' chats are never returned.

**Given** `POST /assistant/chat/messages {text}`
**When** the AI Provider is configured and tested
**Then** the user message is stored, the context is built from rows the caller can read, `chat` is called with a 60 s timeout and one retry outside any DB transaction, the answer is stored and returned, and one `ai_usage` row is written; text over 4,000 characters returns 422.

**Given** the provider is not configured, not tested, or fails
**When** a message is sent
**Then** the response is 502 `ai_provider_failed` or 409 `conflict` with `extensions.check = "not_configured"`, the drawer shows "The assistant can't reach your AI provider. Check AI settings." (Admins see a link), and the rest of the app works.

**Given** `DELETE /assistant/chat`
**When** called
**Then** the chat and its messages are deleted; the drawer shows the greeting again.

**Given** the answer contains a Gown suggestion
**When** validated
**Then** each suggested Gown is shown as a link row (mosaic, name) that opens G2; text that names a Gown the server cannot match is removed.

**Given** a draft reply answer
**When** shown
**Then** it appears as text in the chat with a **Copy** button; no endpoint can place it into the composer or send it.

**Given** the drawer (right, 400)
**When** it opens from the top bar
**Then** it shows the title, **New chat**, close button, the disclosure line, a greeting, three chips, the message list, a typing indicator while waiting, and the input (Enter sends or Shift+Enter per the preference; busy keeps the input editable and disables Send); Esc closes only when no menu or dialog is open.

**Given** a Viewer
**When** the app renders
**Then** the Assistant button is absent and the API returns 403.

**Given** the egress rule
**When** a context block is built
**Then** a unit test asserts no more than 20 items and 2 KB each, no data the caller cannot read, and no field names beyond what is needed; the leak suite also checks that Sentinel client emails are not in the context (email addresses are not sent).

**Given** the leak suite
**When** extended
**Then** Sentinel chat text and answers leave no plaintext in tables, logs or errors.

- Desktop: drawer, chips, message list, copy button, typing indicator, tests, axe.

## Dev record

**Assumptions**
- Migration is `V21__assistant_chat.sql` (the Tasks line says V18; V18 to V20 were taken). One table, `chat_message`; there is no `assistant_chat` table because each User has exactly one chat.
- `chat_message` has no plaintext `seq`. Lines are sorted in memory by decrypted `createdAt` and capped at 100 per User, so the OQ-2 list of seven plaintext-`seq` tables is unchanged.
- "Not configured" means a blank chat model or no base URL (409 `conflict`, `extensions.check = "not_configured"`). The AI settings "tested" status is not enforced.
- Any other provider failure is 502 `ai_provider_failed` with a fixed code and no provider text. A failed call stores nothing, so the question is not kept.
- History sent to the provider is the last 10 stored lines. Keyword routing: summar to SUMMARIZE, draft/reply/respond to DRAFT, gown/dress/suggest/recommend to GOWNS.
- Context sent out is at most 20 items of 2 KB each, with well-formed email addresses removed. Gown items need `PERM_VIEW_GALLERY`. Draft context comes from the open thread (`inquiryId`).
- Gown suggestions are shown only for `[gown:<id>]` tokens that match the offered set; the model cannot invent a Gown link.
- Every endpoint needs `PERM_REPLY`. The assistant has no write path (ArchUnit rule `assistant-has-no-write-path`, with a negative fixture).
