# Story 9.3: Automatic desktop update and release pipeline

As a Staff member on any of the three systems,
I want the app to find, verify and install new versions with my consent,
So that everyone runs the same version without manual reinstalls.

**Assumptions**
- Update host: a separate public releases-only repo that holds signed installers and `latest.json` (OQ-3, approved). The source repo stays private. The repo name and owner are OPEN QUESTION (operator; the update URL constant stays a placeholder `https://github.com/<owner>/<releases-repo>/releases/latest/download/latest.json` until named). The story's test uses a local mock server for the URL.
- No OS signing certificates now. Updates are authenticated by the minisign updater key pair (`TAURI_SIGNING_PRIVATE_KEY` in CI secrets only, offline escrow next to the KEK copies). The public key is embedded in `tauri.conf.json`. The Dev agent generates no real key; a throwaway test key pair is generated in CI for the update test only.
- Spike S-3 (updater on unsigned builds per OS) is the first task: install version A, serve version B from the mock server, check, download, verify, install, restart, confirm the keychain entry still reads. Result recorded in `docs/architecture.md` §9.4 as one line per OS.
- Checks at start and every 24 h. Linux auto-update applies to the AppImage; `.deb` is manual (PRD FR-43).
- The check request carries only app version, OS and architecture (NFR-6); no user id, no token.
- Install waits while `set_dirty(true)` (unsent Draft or Upload review in progress, NFR-3).

**Acceptance Criteria**

**Given** `check_update`
**When** the app starts and every 24 h
**Then** the shell queries the single update URL constant, sends only version, OS and arch, and returns "none", "available(version)" or "failed"; a failure leaves the current version running and shows a non-blocking message only when the User asked for the check.

**Given** an available update
**When** the banner renders
**Then** it reads "Version {x} is ready." with **Install and restart** and **Later**; Later hides it until the next check.

**Given** `install_update`
**When** the User confirms and `set_dirty` is false
**Then** the package is downloaded, its signature is verified against the embedded public key, installation runs and the app restarts; unsigned or tampered packages are rejected (test with a modified file) and the banner shows "The update couldn't be verified. Nothing was changed."

**Given** `set_dirty(true)`
**When** the User presses **Install and restart**
**Then** the dialog "You have unsent work. Finish or discard it first." shows and nothing installs.

**Given** the CI release pipeline (tag `v*`)
**When** it runs
**Then** `tauri-action` builds on the three-OS matrix, produces `.dmg` (arm64 and x64), NSIS/`.msi` (x64), `.AppImage` and `.deb` (x64), generates updater `.sig` files and `latest.json`, and uploads them to the public releases repo with a write token scoped to that repo only; no token or private key appears in logs or artifacts (a log-scan step).

**Given** the install guide
**When** written
**Then** `docs/install-guide.md` documents Gatekeeper (right-click Open, or `xattr -d com.apple.quarantine`), SmartScreen (More info, Run anyway), the Linux AppImage and `.deb` steps and the update behaviour.

**Given** the release checklist
**When** written
**Then** `docs/release-checklist.md` holds the per-OS manual steps: open a `klei://` link, install an update, confirm the refresh token still reads.

**Given** the updater key custody
**When** the story is done
**Then** `infra/ops/key-custody.md` (from 9.2) lists the updater private key, its escrow and the consequence of loss (manual reinstall of every client).

**Given** NFR-1
**When** the update flow runs
**Then** the shell persists nothing but the downloaded package in the OS temp location chosen by the updater plugin, and the Rust no-disk-write test from Story 1.7 allows exactly that path and no other.

**Given** the leak and bundle checks
**When** the build runs
**Then** the bundle scan from Story 1.7 still finds no secret, and the update URL constant is the only network address in `tauri.conf.json` besides CSP.

**Tasks**
- Rust: `check_update`, `install_update` using the Tauri updater plugin, scheduler, tests against a local mock server with a throwaway key.
- Desktop: update banner, dirty-state dialog, tests, axe.
- CI: `.github/workflows/release.yml`, OS smoke matrix reuse, log-scan step; docs: install guide, release checklist.
- Spike S-3 notes.

**Checks**
- `cd desktop && npm test && (cd src-tauri && cargo test && cargo clippy -- -D warnings)`
- `cd backend && ./mvnw verify` (unchanged, green)
- `docker compose -f infra/docker-compose.yml --profile dev up -d --wait && infra/ci/smoke.sh`
- Manual per OS before the first release: the checklist steps (S-3).

**Assumptions**
- `tauri.conf.json` carries placeholders `OWNER/RELEASES_REPO` and `REPLACE_WITH_UPDATER_PUBLIC_KEY`; the operator replaces them with the real releases repo and the real public key before the first tag. `release.yml` fails on a placeholder, `cargo test` passes with it.
- UX spec wording "Restart and install" differs from this story; the story's "Install and restart" wins.
- Test fixtures under `desktop/src-tauri/tests/fixtures/update/` use a throwaway key pair whose private half is not in the repo.

**Not verified**
- Real install and relaunch on macOS, Windows, Linux (S-3): `install` replaces the test binary, so no test calls it. Manual steps are in `docs/release-checklist.md`.
- `release.yml` has never run (no repository, no secrets); `tauri-action` argument names checked against its documented inputs only. Gatekeeper/SmartScreen wording on current OS versions.
- Real-OS look of the banner and dialog; `.deb` and AppImage behaviour.

**Shortcuts**
- One flat 15-minute download timeout (per-chunk stall timeout when installers pass ~100 MB).
- Schedule lives in the webview (24 h timer while the app runs), not in Rust; a closed app checks at next start.
- Banner state is not saved; a dismissed banner returns at the next look.
- `install_update` asks the feed again before downloading (no cached `Update` across calls).
- No download progress shown, only a disabled button.
- Installer install-and-launch is the manual checklist, not CI.
