# Story 11.14: Two-factor authentication

As a Staff member or Admin,
I want to add a second step to my sign-in with an authenticator app,
So that a stolen password alone cannot open the studio's client data.

**Assumptions**
- New requirement **FR-44**, added to `docs/prd.md` by this story. The PRD did not mention 2FA; `ux-spec.md` lines 149 and 228 removed the card as "Deferred". The user chose "build all, full stack" on 2026-11-10.
- TOTP per RFC 6238: 6 digits, 30 s step, HMAC-SHA1 (authenticator-app default), accepting the current step and one step either side. Built on the JDK (`javax.crypto.Mac`); no new dependency for the code itself.
- 2FA-1 APPROVED (2026-11-10): add `com.google.zxing:core` (one small, widely used library) to draw the `otpauth://` URI, server-side as an SVG/PNG data URI; the secret is also shown as text for manual entry.
- 2FA-2 DECIDED (2026-11-10, the user's reply "yes" to item 4 was read as accepting the defaults): the "2FA requirement" for Admins (the prototype shows only an audit-log sample line) is not built; 2FA is optional per user. Say so in the Dev record. If the user meant yes to a requirement, add a story.
- Sign-in lives on Auth Web (`AuthorizeController`, `login.html`); the desktop PKCE flow (Story 1.5) does not change, the code step is an extra page inside the browser sign-in. The refresh flow does not ask for a code.
- Secret storage: `totp_secret_ct` encrypted with the existing field codec (NFR-1), never returned after enrolment. Recovery codes: 8 random codes of 10 characters, shown once, stored as hashes (the same password hashing the app uses, `PasswordChangeService`/`CredentialService`), each usable once.
- Rate limiting: the existing `RateLimiter` (5 failures per account or 20 per IP in 15 minutes, doubling delay). TOTP failures count on the same account key as password failures. `shortcut:` in memory per instance, as that class already notes.
- Replay: a code (time step) accepted once is rejected again for the same user; stored as `last_used_step`.
- Turning 2FA off requires the current password and a valid code. A lost device is handled by recovery codes; an Admin can reset a user's 2FA from Staff (audit logged), which is the only recovery without codes.
- New ADR in `docs/architecture.md` (TOTP, storage, replay, reset). Migration `V25__totp.sql` (next free number at build time).

**Acceptance Criteria**

**Given** Settings › Profile
**When** it renders
**Then** a card "Two-factor authentication" shows the row "Authenticator app" with "Add a second step when you sign in. Recommended for admins." and a gray "Off" pill with **Set up**; when on, "Enabled. You’ll enter a 6-digit code at sign-in.", a green "On" pill and **Turn off**.

**Given** **Set up**
**When** pressed
**Then** the dialog "Set up authenticator" shows the QR code (2FA-1) with `role="img"` and an accessible name, the secret as text, the line "Scan with an authenticator app, then enter the 6-digit code." and a field "6-digit code"; a correct code enables 2FA, shows the 8 recovery codes once with **Copy** and **I saved them**, and the toast reads "Two-factor enabled"; a wrong code shows "That code is incorrect or has expired." and does not enable.

**Given** `POST /api/v1/me/2fa/start` and `POST /api/v1/me/2fa/confirm`
**When** called
**Then** `start` creates a pending secret (replacing an older pending one, not an active one) and returns the `otpauth://` URI and the secret once; `confirm` verifies the code, activates, and returns the recovery codes once; both need the caller's session, are rate-limited, and write `TWOFA_ENABLED` to the audit log.

**Given** a user with 2FA on signs in on Auth Web with the right password
**When** the form is accepted
**Then** a second page "Enter your code" asks for the 6-digit code (or a recovery code via "Use a recovery code"), and only a valid one completes the PKCE redirect; no authorisation code exists before then.

**Given** a wrong or reused code
**When** submitted
**Then** the page shows "That code is incorrect or has expired." in the same time and wording as a wrong password path, the failure counts in `RateLimiter`, a lockout shows the existing lockout copy, and `SIGN_IN_2FA_FAILED` is audited (the code itself is never logged).

**Given** a code from the previous, current or next step
**When** it was not used before
**Then** it is accepted once; the same step used twice is rejected (replay test with a fixed `Clock`); a step two away is rejected.

**Given** a recovery code
**When** used
**Then** it works once, the remaining count shows in Profile ("{n} recovery codes left"), and **Make new codes** (password + code required) replaces all of them.

**Given** **Turn off**
**When** pressed
**Then** the dialog "Turn off two-factor?" with "Your account will be less secure. You can set it up again at any time." asks for password and code, then clears the secret and codes, writes `TWOFA_DISABLED`, and the toast reads "Two-factor turned off".

**Given** an Admin on Staff › Edit staff member
**When** **Reset two-factor** is pressed for another user
**Then** the user's 2FA is cleared, `TWOFA_RESET` is audited with the actor, and that user is asked to set it up again by a banner in Profile; Staff without the permission do not see the button.

**Given** the leak suite
**When** extended
**Then** `totp_secret_ct` and the recovery hashes appear only as envelopes or hashes, no secret, code or `otpauth://` URI appears in logs, `ai_usage`, the audit detail or error bodies, and the start response is not stored.

**Given** the TOTP implementation
**When** unit-tested
**Then** the RFC 6238 test vectors pass for SHA-1 at the standard times, and base32 encode/decode round-trips.
