# Story 7.4: Status and Client edits

As a Staff member,
I want to set an inquiry's status and fix a client's details,
So that the inbox reflects reality and the client record stays right.

**Assumptions**
- A Client message arriving on a Closed Inquiry reopens it automatically (AD-21). No intake exists yet, so the rule is implemented in `InquiryStateService` and covered by a unit test only.
- Moving an Inquiry out of Closed needs `PERM_CLOSE_INQUIRY` (A9). The PRD is silent; Gate 5 confirms.
- Editing a Client needs `PERM_REPLY` (PRD FR-23 marks it ASSUMPTION).
- Phone, city, wedding date, source (a fixed set: Website, Instagram, Referral, Event, Other), note (up to 2,000 characters). Name and email are read-only here; email is the Client's blind-index key `[ASSUMPTION]`.

**Acceptance Criteria**

**Given** `PATCH /inquiries/{id} {status}` with `If-Match`
**When** the new status is New, Replied or Closed
**Then** `status_ct` and `status_bidx` are updated together, `InquiryStateService` is the only writer, an Audit Entry `inquiry_status_changed` (old and new, encrypted) is written, and the new version returns; Closed requires `PERM_CLOSE_INQUIRY` (403 otherwise, itself audited); moving out of Closed also requires it.

**Given** a stale version
**When** sent
**Then** 409 `conflict`.

**Given** the thread header
**When** the status select changes or **Close inquiry** is pressed
**Then** the pill and list update at once, the toast reads "Marked {status}" or "Inquiry closed", and **Close inquiry** is disabled with the tooltip "You don't have permission to close inquiries." for a User without it; on a Closed Inquiry **Reopen** replaces it.

**Given** `PATCH /clients/{id}` with `If-Match` and `PERM_REPLY`
**When** applied
**Then** fields are validated (phone up to 40 characters, wedding date a date, source from the set, note up to 2,000), encrypted, the response carries the new version, and `TermIndexer` re-runs for the Client's Inquiries only when the name changes (it is read-only here, so this is a no-op test).

**Given** I2
**When** **Edit** is pressed
**Then** a dialog edits phone, city, wedding date, source, note; **Save** shows the toast "Client updated"; 409 shows the standard conflict message; Viewer cannot reach I2.

**Given** a Client message simulated through the service
**When** it arrives on a Closed Inquiry
**Then** the Inquiry becomes New and unread, `seq` is touched, and the sidebar count rises (unit test).

**Given** the leak suite
**When** extended
**Then** Sentinel Client edits and status values leave no plaintext; `status_bidx` values are the expected 32-byte HMACs and differ across the three statuses.

**Tasks**
- Backend: `InquiryStatusService`, `ClientEditService`, `InquiryStateService.reopenOnClientMessage`, tests.
- Desktop: status select, Close/Reopen, Client edit dialog, tests, axe.

**Checks**
- `cd backend && ./mvnw verify`
- `cd desktop && npm test && (cd src-tauri && cargo test)`
- `docker compose -f infra/docker-compose.yml --profile dev up -d --wait && infra/ci/smoke.sh` (extend: close an inquiry, filter Closed returns it).

## Dev record

**Assumptions**
- Closed needs `PERM_CLOSE_INQUIRY` both into and out of Closed. Refusal is 403 plus the existing `forbidden` audit entry.
- A status change does not touch `seq`, so list order stays. Same-status PATCH is a no-op: 200, same version, no audit.
- `PATCH /api/v1/clients/{id}` replaces all five fields (blank clears). `If-Match` required (400 without), stale 409. City max 80 chars and one line; phone, source, note, weddingDate rules as in 7.2 column limits. Lengths count UTF-16 units.
- Name and email stay read-only: no `TermIndexer` rerun.
- No audit entry for a Client edit. Status change audits `INQUIRY_STATUS_CHANGED`, detail `"old to new"`, actor name.
- `reopenOnClientMessage` is covered by integration test only (no intake until deferred feature).
- UI updates when the server answers, not before. Edit client Cancel asks nothing. Thread version is read again after a Reply.
