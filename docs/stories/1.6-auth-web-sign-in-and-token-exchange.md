# Story 1.6: Auth Web sign-in and token exchange

As a Staff member,
I want to sign in on a server-rendered page in my browser and get back a code the desktop app can trade for tokens,
So that my password never enters the app.

**Assumptions**
- Pages A1 (sign in) and A6 (return) only. A2 to A5 come in Epic 2.
- Auth mail is not needed here. The refresh and credential tables are created here: `refresh_token`.
- `tokens.css` is generated by a script in `infra/ci/` from `DESIGN.md` (UX-DR1); Inter is bundled under `static/` (UX-DR3).

**Acceptance Criteria**

**Given** `GET :8081/authorize?client=desktop&challenge=…&state=…&redirect=…`
**When** `redirect` is not exactly `klei://auth/callback` or `http://127.0.0.1:<1024-65535>/callback` with no userinfo and no query
**Then** a 400 page is returned and no redirect happens (AD-8).

**Given** a valid authorize request
**When** the login page (A1) loads
**Then** it shows email, password with show/hide, "Keep me signed in", **Sign in**, "Forgot password?" and the helper "Have an invite? Open the link in your email."; it asks for the password even if a cookie session exists.

**Given** correct credentials
**When** the form is posted with the CSRF token
**Then** the code (60 s, single use, bound to client, redirect and challenge) is issued, the cookie session is destroyed, and the browser is redirected to `redirect?code=…&state=…`; page A6 shows "You're signed in" with **Open Klei Bridal**.

**Given** a wrong email or a wrong password
**When** posted
**Then** the same message "Email or password is incorrect." appears, a dummy Argon2id verify runs for unknown emails so timing is equal, the email keeps its value and the password clears.

**Given** 5 failed attempts per account or 20 per IP in 15 minutes
**When** another is posted
**Then** it shows "Too many attempts. Try again in {n} minutes." with exponential delay; only a lockout writes an Audit Entry; successes and failures of sign-in write `sign_in` and `sign_in_failed` entries.

**Given** `POST /api/v1/auth/token {code, verifier}`
**When** the verifier's S256 hash matches the challenge
**Then** it returns an access JWT and an opaque 256-bit refresh token (hash in `token_bidx`, 24 h, or 30 days with Keep me signed in).

**Given** `POST /api/v1/auth/refresh`
**When** a refresh token is used once, again within 10 s, and again after 10 s
**Then** the first rotates, the second returns the same successor, the third revokes the whole family and writes an Audit Entry.

**Given** `POST /api/v1/auth/logout`
**When** called
**Then** the family is revoked and the `sid` is added to the in-memory revoked set.

**Given** a disabled or deleted User
**When** refresh is attempted
**Then** it is refused.

**Given** a User whose Role holds no Permission at all
**When** they submit correct credentials, or refresh is attempted
**Then** no code or token is issued, the page shows "Your account has no access yet. Ask an admin.", and an Audit Entry is written. The message appears only after a correct password, so it reveals nothing to someone guessing emails.

**Given** the pages
**When** headers are inspected
**Then** CSP `default-src 'self'; frame-ancestors 'none'`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, cookie `__Host-` HttpOnly Secure SameSite=Lax; pages work without script; axe-core finds no serious issue on A1 and A6.

**Given** the leak suite
**When** extended
**Then** it signs in with Sentinel credentials, drives wrong passwords, and asserts no Sentinel in tables, logs or access logs.

**Tasks**
- `AuthorizeController`, Thymeleaf templates `login`, `return`, `error`, `static/fragment.js` stub (used in Epic 2), `tokens.css` generator, Inter files.
- `AuthCodeStore` (memory), `RateLimiter` (memory), `TokenEndpoint`, `RefreshService`, `V4__refresh_token.sql`.
- Scripted Auth Web flow helper for tests and `smoke.sh` (HTML form post with cookie jar and CSRF extraction).

**Checks**
- `cd backend && ./mvnw verify`
- `docker compose -f infra/docker-compose.yml --profile dev up -d --wait && infra/ci/smoke.sh` (bootstrap Admin signs in through the scripted flow and `GET /api/v1/me` returns the Admin).

**Deviations**
- Migration is `V5__refresh_token.sql` (V4 is `V4__SeedRoles`), and the token endpoint is `AuthTokenController`, not `TokenEndpoint`.
- Audit policy follows architecture, not the AC line "sign_in / sign_in_failed entries": only lockout (`sign_in_locked`), no-access (`sign_in_no_access`) and `refresh_reuse` are audited. Routine success and failure would flood the log and the AC's own earlier line says only a lockout writes an entry. `smoke.sh` asserts the audit count stays at one after a successful sign-in.
- "Disabled or deleted" means user missing or `status != ACTIVE` (`UserStatus` has only ACTIVE and INVITED).
- Auth Web CSRF uses the Spring session synchroniser token; a failed check forwards to `/login/denied` (400 error page). Session cookie `__Host-klei-auth` is Secure, so tests and smoke carry it by hand.
- `SentinelCatalog.captured` holds run-time Sentinels (code, access token, refresh token); `refresh_token` columns map to empty lists.
- `infra/ci/package.json` (axe-core, puppeteer-core) added; `.gitignore` gains `node_modules/` and `target/`.

**Shortcuts and risk.** `AuthCodeStore` and `RateLimiter` are in memory and per instance: a restart drops pending codes and forgets lockouts (accepted, single backend). Two concurrent refreshes of one token can meet in the `@Version` check and the loser gets a 500; the client retries and lands in the 10 s grace. `axe.mjs` is not wired into `verify` (needs Chrome); run it after `verify`. First Thymeleaf build needs network. Story 1.7 consumes `klei://auth/callback` and the token API.
