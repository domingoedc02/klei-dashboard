# Story 11.13: Email notifications and digest

As a Staff member,
I want to choose which events also reach me by email, and how often,
So that I hear about a new inquiry without keeping the app open.

**Assumptions**
- Reinstates the email half of FR-34, `DEFERRED` at Gate 3 (`ux-spec.md` lines 232-233). The user chose "build all, full stack" and "store and send" on 2026-11-10. In-app toggles stay as built (Story 6.3).
- Events (prototype): New inquiry, AI finished processing, Team activity. The three existing types (`NotificationType.NEW_INQUIRY`, `AI_FINISHED`, `TEAM_ACTIVITY`). One email toggle per event, per user, default off (an email nobody asked for is worse than a missing one). `[ASSUMPTION]`
- **Email digest** frequency (prototype): Real-time, Hourly, Daily, Weekly, Never. Default "Never". "Real-time" sends one mail per event at once. Hourly, Daily and Weekly collect events since the last digest and send one mail when due. "Never" overrides the toggles: nothing is emailed.
- Daily is sent at 08:00 and Weekly on Monday 08:00 in the user's preference time zone (UTC when unset). `[ASSUMPTION]`
- Scheduling: `@EnableScheduling` is already on (`KleiApplication.kt`, example `ObjectSweepJob`). One job runs every 5 minutes, finds due users, sends, and records `last_digest_at` per user. `shortcut:` in-process, one instance; a second instance would double-send, so add a row lock (`select … for update skip locked`) now, which makes it safe to scale later.
- Mail body carries titles only, as the in-app bell does ("New inquiry from {first}"); no inquiry text, no email address of the client, no filename. The notification `title` field is already built by callers and is treated as untrusted text.
- Every mail ends with a plain line "Change what you get by email in Settings › Notifications." No unsubscribe link (no public endpoint).
- Mail failures are logged by class name only; the in-app notification is the source of truth, so a lost mail is not retried and the digest cursor still advances. `[ASSUMPTION]`

**Acceptance Criteria**

**Given** Settings › Notifications
**When** it renders
**Then** the table has columns **Event**, **Email**, **In-app** with the three events (name and helper text as the prototype: "When a client submits the website form", "When a batch is ready to review", "Invites accepted and role changes"), a switch in each cell with an accessible name "{event} by email" / "{event} in-app", and below it a select **Email digest** with Real-time, Hourly, Daily, Weekly, Never.

**Given** a toggle or the digest select changes
**When** it saves
**Then** the toast reads "Preference saved" or "Digest set to {frequency}"; `PUT /api/v1/me/preferences` stores `emailNewInquiry`, `emailAiFinished`, `emailTeamActivity` and `digest` with the existing `version`/409 behaviour (extend `Prefs` with a schema bump so old rows read as off and Never).

**Given** digest Real-time and an email toggle on
**When** `NotificationService.notify` creates a row for that user
**Then** one `NOTIFY` mail with the title is sent after the transaction commits (not inside it); toggle off or digest Never sends nothing; a user who is not Active gets nothing.

**Given** digest Hourly, Daily or Weekly
**When** the job runs at or after the due time
**Then** one `DIGEST` mail lists the notification titles created since `last_digest_at` (newest first, at most 50, then "and {n} more"), and `last_digest_at` advances; no notifications means no mail; running the job twice in the same minute sends once.

**Given** the mail templates `NOTIFY` and `DIGEST`
**When** tested
**Then** `MailTemplateTest` shows each carries only the allowed variables (`title`, or `items` and `more`), refuses any other key, and a leak test proves a Sentinel placed in an inquiry body, a client email or a filename never appears in the mail.

**Given** the leak suite
**When** extended
**Then** the stored preference envelope holds no readable address and `notification.title` plus mail output stay free of Sentinels.

**Given** two backend instances run the job
**When** both wake at once
**Then** only one sends for a given user (`skip locked` test with two threads).
