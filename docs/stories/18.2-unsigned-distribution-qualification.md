# Story 18.2: Unsigned distribution qualification

As the app owner, I want accurate unsigned-install guidance and a checksum publication procedure, so that staff can assess installer provenance and OS warnings without being told to bypass security controls.

**Assumptions**
- No paid Apple Developer membership or signing/notarization credentials are assumed; unsigned qualification is not equivalent to package authenticity or a Gatekeeper bypass.
- The release host is the download site (OQ-M3 resolved by the owner, story 18.5). No certificates are used because the app is for internal use only; SHA-256 values shown beside each file are optional and prove integrity relative to the site, not publisher identity.

**Acceptance Criteria**

**Given** macOS, Windows and Linux unsigned installers
**When** first-launch behavior is qualified on each target OS
**Then** observed Gatekeeper, SmartScreen and Linux behavior is recorded with OS/version, package hash and exact user-visible prompts; no warning is described as resolved by a manual update.

**Given** the Electron installation guide
**When** a staff user follows its macOS and Windows warning steps
**Then** it documents only user-initiated Finder right-click **Open** and Windows **More info**; it does not recommend disabling protections, shell quarantine removal, registry edits or running untrusted files.

**Given** checksum publication
**When** an Electron release is prepared
**Then** the release procedure generates a SHA-256 value for each installer and the download site (18.5) shows it beside that file; comparison is optional, and no document describes it as proof of publisher identity.

**Given** documentation is created
**When** migration docs are reviewed
**Then** only `docs/install-guide-electron.md` is added/edited by this story; existing `docs/install-guide.md` remains byte-for-byte unchanged.

**Tasks**
- `docs/install-guide-electron.md`: document unsigned first launch, per-OS package selection, safe user-initiated warning steps, manual updates from the download site and limits of checksums.
- `electron/test/release-integrity.test.ts`: assert installer checksum generation/verification instructions and prevent release configuration from claiming signing/notarization.
- Release operator: record the OQ-M5 server details and the SHA-256 format shown by the site before distribution; capture per-OS observed prompts and installer SHA-256 values.

**Dev notes**
- Reference existing legacy guidance `docs/install-guide.md` only for historical comparison; do not edit or copy obsolete commands as Electron guidance.
- No Rust source is ported. Rust release behavior reference is `desktop/src-tauri/src/update.rs::{check,download,Ready::install}` and behavior specification is `desktop/src-tauri/src/update_tests.rs`; the Electron story explicitly does not inherit signature-verification promises.
- Existing `.github/workflows/release.yml`, `desktop/src-tauri/tauri.release.conf.json` and `docs/release-checklist.md` remain protected and unchanged.

**Testing**
- Run doc/link checks and the Electron release-integrity unit check; manually qualify first launch on each target OS and attach exact observed warnings/hashes to the Electron release record.
- Verify no advice implies disabling OS protection or that checksums alone establish publisher identity.

**Prototype unchanged check**
- Require baseline protected-path diff empty and untracked audit limited to the approved new Electron install guide and Electron files.
- Confirm original install guide, release checklist and visible Tauri UI behavior remain unchanged; compare the Electron user-facing download guidance for truthful parity exception wording.
