# Story 12.13: Assistant drawer, desktop sign-in and Auth Web polish

As a Staff member,
I want the AI Assistant drawer and the sign-in pages to behave and read like the approved prototype,
So that keyboard and screen-reader use is predictable and the sign-in screens look finished.

**Assumptions**
- Audit row G-27. Template and CSS changes only on the Auth Web side; **no backend logic change** and no new dependency.
- Prototype assistant: `js/assistant.js:34-39` `ai-panel` head with avatar, h2, **New chat** icon button and **Close** icon button; `ai-msgs` has `role="log" tabindex="0"`; `css/shell.css:79-97`.
- Prototype auth: `js/auth.js:18-19` `btn btn-primary btn-block` with a spinner while busy; `:30` login foot "Have an invite? Accept invitation"; `:48-49` verify code/link segmented toggle; `:56`, `:69`, `:77` foot "Back to sign in"; `css/base.css:51` `.btn-block`, `:53` `.spinner`.
- App assistant today: `Shell.tsx:105-111` drawer head with a `×` `link` as close (`:109`); `:277-285` the **AI Assistant** top-bar button has no `aria-expanded` or `aria-controls` (12.4 adds them; this story does not redo that); `Assistant.tsx:91` `role="log"` without `tabIndex`, `:127` **New chat** is a footer `link`.
- App sign-in today: `App.tsx:28` `Button`, `:87` boot text "Loading…", `:102`, `:123-124` two keychain buttons with no spacing.
- Auth Web templates (`backend/app/src/main/resources/templates/`): `login.html:42` ("Have an invite? Open the link in your email."), `forgot.html:30`, `:42`, `verify.html:64`, `code.html:41`, `reset.html:76` ("Back to Klei Bridal" linking to `/return`); styles `static/auth.css`, behaviour `static/auth.js`.
- **Constraint (accepted deviation, recorded):** the prototype's "Back to sign in" goes to its in-page login. In the real flow, sign-in needs the app's PKCE request, so the link must keep pointing at `/return` (11.3 shortcut). This story changes only the **label** to "Back to sign in"; the target is unchanged.
- **Verify toggle:** the prototype's code/link toggle on the verify page is **accepted as a deviation** (the page already presents the one method the server supports; a second control with nothing behind it would be unreachable UI). Recorded in `docs/ux-spec.md`. If the maintainers want it, it is a new story.
- **Invite foot:** "Have an invite? Accept invitation" cannot link anywhere useful (invites arrive by email link). Template keeps the text "Have an invite? Open the link in your email." — accepted deviation.
- Assistant Enter-to-send is gated by the `enterToSend` preference; confirm this is intended before changing it (not changed here).
- 11.3 and 11.11 stay `done`; this story corrects them.

**Acceptance Criteria**

**Given** the Assistant drawer is open
**Then** its head has a title, a **New chat** icon button and a **Close** icon button (`aria-label` set, visible focus ring), replacing the `×` link and the footer **New chat** link (prototype `assistant.js:34-39`).
Test: update `Assistant.test.tsx:52` (New chat in the head), `:67`, `:72`; `Shell.test.tsx` `it('closes the drawer with the Close button and returns focus to AI Assistant')`.

**Given** the message log
**Then** it is `role="log"` with `tabIndex={0}` and an accessible name, so keyboard users can scroll it (prototype `assistant.js` `ai-msgs`).
Test: `Assistant.test.tsx` `it('makes the message log focusable')`; axe stays at zero violations.

**Given** the desktop sign-in screen
**Then** the primary action is a full-width button (`.btn.block` from 12.3) that shows a spinner while busy; the two keychain buttons are spaced by `--space-3`; the boot screen shows a skeleton (not the text "Loading…") with `role="status"` and an accessible label.
Test: update `App.test.tsx:32`, `:42`, `:59`; `it('shows the boot skeleton with a status role')`.

**Given** the Auth Web pages `forgot.html`, `verify.html`, `code.html`, `reset.html`
**Then** the footer link text is "Back to sign in" and its `href` is still `/return`; `login.html:42` reads as before.
Test: `authweb.test.ts` `it('uses Back to sign in and keeps the /return target')`; `node infra/ci/axe.mjs` reports zero serious or critical violations (needs `./mvnw verify` to build `backend/app/target/auth-pages`, and Chrome).

**Given** `node infra/ci/shots.mjs --only assistant-open` and `--only sign-in` (the 12.1 screenshot command)
**When** run at 1100x700 and 1280x800
**Then** `report.json` shows no failure; the PNGs match the prototype assistant drawer and sign-in screens (head buttons, block primary, spaced keychain buttons). Auth Web pages are checked with `node infra/ci/axe.mjs` and by eye, because 12.1 does not render them.
