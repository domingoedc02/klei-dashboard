# Story 9.2: Key rotation and re-wrap

As an operator,
I want to introduce a new master key and move all stored data keys to it without downtime,
So that I can retire a key without losing data.

**Assumptions**
- Four-deploy flow from architecture §5.4. This story builds step 3 (re-wrap) and the status view; steps 1, 2 and 4 are operator actions on the environment.
- Re-wrap touches `data_key` and `stored_object` only, by raw JDBC (`KeyRotation`); the entity listener never fires, and no `*_ct` column or S3 object changes.
- `PERM_KEY_ROTATE` is Admin-only and not editable (PRD delta recorded in §12 of the architecture).
- The Key Management view is a small panel in Settings > Admin tabs. The PRD's FR-41 calls the actor an "operator"; here the Admin is the operator.
- OPEN QUESTION (OQ-5, non-blocking): who holds the offline copy of the KEK, `KLEI_BIDX_KEY` and `KLEI_JWT_KEY`, and the rotation cadence. Default: the user, yearly and on staff exit. The Story ships `infra/ops/key-custody.md` stating this default with a blank "Holder" line to be filled by a human.
- Losing every KEK copy loses all data; `infra/ops/key-custody.md` opens with that sentence.
- The Audit registry from Story 2.5 must be empty after this story (all FR-40 actions exist).

**Acceptance Criteria**

**Given** `GET /admin/keys/status` with `PERM_KEY_ROTATE`
**When** called
**Then** it returns `{active, configured:[n…], rows:{dataKey:{n:count}, storedObject:{n:count}}}` with counts per `kek_version`, never key material or ids.

**Given** `POST /admin/keys/rewrap`
**When** the active KEK is not the highest configured version
**Then** it returns 409 `conflict` and does nothing.

**Given** the active KEK is the highest
**When** the job runs
**Then** it pages rows with `kek_version < active` in transactions of 500, unwraps with the old KEK, wraps with the new (AAD `dek|<id>`), and updates by raw JDBC; it is resumable by the predicate and idempotent (a second run changes nothing); reads keep working at every moment (test reads during the run); an Audit Entry `key_rotation` with counts is written on completion; a concurrent second start returns 409.

**Given** step 4 (old KEK removed from the environment)
**When** the app starts while a row still references that version
**Then** boot fails naming the version number; with zero such rows it boots.

**Given** the end-to-end rotation test
**When** it runs (Testcontainers, env overridden per phase)
**Then** it creates data of every kind, rotates to `KLEI_KEK_ACTIVE=2`, re-wraps, removes KEK 1, restarts, and every row and object still decrypts; the full leak suite (FR-42) is repeated after rotation.

**Given** the Key panel
**When** it renders
**Then** it shows the active version, configured versions, rows per version, **Re-wrap now** (disabled with a reason when not allowed or nothing to do), a progress line while running (polled every 2 s) and the result; Loading and Error states exist; it is absent without the Permission.

**Given** the leak suite
**When** extended
**Then** it asserts that `GET /admin/keys/status` and every log line during the job contain no key bytes and no wrapped DEK.

**Given** FR-42 closure
**When** `./mvnw verify` runs
**Then** the leak suite covers every catalogue entry in architecture §5.7 (users, Clients, Inquiries and Replies, Gown names, descriptions and attributes, AI settings, prompts, audit actions, filenames, chat, attachments), and a registry test fails if any `@EncryptedEntity` has no Sentinel.

**Tasks**
- Backend: `RewrapJob`, `KeyRotation` use, `KeyStatusController`, boot check for missing KEK versions, rotation integration test, `SentinelCatalog` completeness test, `infra/ops/key-custody.md`.
- Desktop: Key panel, polling, tests, axe.

**Checks**
- `cd backend && ./mvnw verify`
- `cd desktop && npm test && (cd src-tauri && cargo test)`
- `docker compose -f infra/docker-compose.yml --profile dev up -d --wait && infra/ci/smoke.sh` (extend: status endpoint responds for the bootstrap Admin; re-wrap with nothing to do returns 200 and zero counts).

## Dev record

**Assumptions**
- `GET /api/v1/admin/keys/status` answers `{active, highest, configured:[n], rows:{dataKey:{"n":count}, storedObject:{"n":count}}, run:{state, total, dataKey, storedObject, kek}}`; counts are keyed by version string. `state` is `idle|running|done|failed`, kept per process, so it reads `done` after a finished run.
- `POST /api/v1/admin/keys/rewrap` answers 202 when a run starts, 200 `idle` with zero counts when nothing is left, 409 `conflict` with `extensions.check` `active_not_highest` or `in_progress`.
- Compose forwards `KLEI_KEK_1..4` (blank by default). `KeyRing` ignores a blank non-active slot; a blank active slot still fails boot as `missing_kek`.
- Boot check (`CryptoSelfTest`, `@Order(1)`) names the missing `KLEI_KEK_n` when any `data_key` or `stored_object` row needs it; empty tables pass.
- Audit `KEY_ROTATION` detail `dataKey=N storedObject=M kek=K`; Admins get a `TEAM_ACTIVITY` notification "Keys re-wrapped to version K" (target `settings`), closing the 8.1 producer gap.
- `Holder` line in `infra/ops/key-custody.md` stays blank (OQ-5, human to fill).
- BIDX and JWT key rotation are out of scope (re-hash / re-issue, not re-wrap).
