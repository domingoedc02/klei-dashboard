# Story 16.5: Deep link, single instance and loopback

As a User, I want the browser to return me to the app after sign-in on every supported OS, without the preview app taking over the Tauri app's `klei://` link, so that both can be installed side by side.

**Assumptions**
- The preview uses the loopback redirect only (AD-27, OQ-M4, resolved for the preview) and does **not** register `klei://`. The code for the deep link callback is still ported and unit-tested, and stays disabled in preview builds. Registration is reconsidered only at cutover by the owner (OQ-M4).
- Loopback behaviour comes from `desktop/src-tauri/src/loopback.rs`. Spike 3 (14.3) confirms the preview and Tauri coexist.
- Single-instance behaviour: a second launch focuses the first window.

**Acceptance Criteria**

**Given** loopback mode
**When** `sign_in` starts
**Then** a TCP listener binds `127.0.0.1` on an OS-chosen port that is at least 1024 (loopback only, never `0.0.0.0` or `::`; the backend rejects ports below 1024), the redirect is `http://127.0.0.1:<port>/callback`, and the listener is closed after the single callback or the 300 s timeout.

**Given** the loopback listener
**When** requests arrive
**Then** only `GET` to path `/callback` counts; any other path answers 404 "Not found" and keeps listening; empty speculative connections are ignored; a request head is read for at most 5 s and 8192 bytes; after the one `/callback` request it answers and closes.

**Given** the loopback response
**When** sent
**Then** it is `text/html; charset=utf-8` with `Cache-Control: no-store`, `Content-Security-Policy: default-src 'none'`, `Connection: close`, status 200, and the text "You're signed in. You can return to Klei Bridal." on success or "Sign-in didn't finish. Return to Klei Bridal and try again." on failure.

**Given** the deep-link handler (`klei://auth/callback`, disabled in preview)
**When** enabled in a test build
**Then** only URLs with scheme `klei`, host `auth` and path `/callback` are accepted; others are ignored; the launch-URL case (app started by the link) is handled.

**Given** a second app launch
**When** the preview's single-instance lock is held
**Then** the first window is focused and restored if minimised, and no second window opens.

**Given** the preview app and the Tauri app both installed
**When** the browser returns to `klei://auth/callback`
**Then** the preview never receives it (it registered nothing), and the Tauri app is unaffected; spike 3 evidence is linked in the story.

**Tasks**
- `electron/src/main/auth.ts`: `serveLoopback(listener, session)`, `readTarget`, `respond`.
- `electron/src/main/session.ts`: loopback choice by config (`loopback: true` default for preview).
- `electron/src/main/deeplink.ts`: URL filter, `open-url` (macOS) and `second-instance` argv (Windows/Linux) handling, off by default.
- `electron/src/main/index.ts`: single-instance wiring from 15.1.
- `electron/test/loopback.test.ts`: speculative connection ignored, stray path 404, one callback ends the listener, bind address is `127.0.0.1`.
- `electron/test/deeplink.test.ts`: accept/ignore table.
- Update note: in `docs/planning-artifacts/electron-migration/spike-3-protocol-coexistence.md` link the evidence.

**Dev notes**
- Port from `loopback.rs` (`serve`, `read_target`, `respond`) and `lib.rs::on_urls`. In Tauri, Linux falls back to loopback when `klei` cannot be registered; preview always uses loopback.
- Cutover with `klei://` ownership is OQ-M4; do not call `setAsDefaultProtocolClient` in preview.

**Testing**
- Run the unit tests. Real browser round trip on each OS and a run with Tauri open are manual checks in 20.1.

**Prototype unchanged check**
- Require the 14.1 gate. Tauri's `klei://` registration (check with the OS's handler list) is unchanged after installing and removing the preview.

**Dev Agent Record**
- `main/auth.ts`: `loopbackRedirect` (a `StartRedirect`): Node `http` server on `127.0.0.1` port 0, re-bound if the OS gives a port below 1024 (up to 10 tries, then `failed` "no loopback port"). Only `GET /callback` counts; anything else answers 404 "Not found" and keeps listening. Empty speculative connections never reach the handler. Header read limit 8192 bytes and `headersTimeout` 5 s. After the one callback it answers 200 (`text/html; charset=utf-8`, `Cache-Control: no-store`, `Content-Security-Policy: default-src 'none'`, `Connection: close`) with the success or failure text, then closes. The session also calls `stop()` on timeout, cancel or completion.
- `index.ts` passes `loopbackRedirect`; `KLEI_LOOPBACK` and `Config.loopback` are gone, since the preview has no other mode (AD-27, OQ-M4).
- `main/deeplink.ts`: `parseCallback` (scheme `klei`, host `auth`, path `/callback` only) and `attachDeepLink` (`open-url`, `second-instance` argv, launch argv). Unit-tested, not imported by `index.ts`, never registers the scheme. `contract.test.ts` asserts no `setAsDefaultProtocolClient`/`removeAsDefaultProtocolClient` in main and no `attachDeepLink` in `index.ts`; its remote-URL scan now allows `http://127.0.0.1...` (loopback only).
- Single instance: unchanged from 15.1 (`requestSingleInstanceLock`, `second-instance` runs `focusMainWindow`, which restores a minimised window). Spike 3 covered the lock.
- Tests: `loopback.test.ts` (6: bind and port, empty and stray and POST ignored, headers and body of the answer, failure page leaks no error text, `stop`, end to end with `Session`, timeout closes the listener), `deeplink.test.ts` (3).
- Full suite 122 pass, typecheck clean, gate passes.
- Not verified: a real browser round trip against the compose backend (20.1); Windows and Linux; a run with the installed Tauri app open. The deep link path is unit-tested only.
